# ZGMINI 공통 작업 대기열 도입 — 최상위 목표·실행 계획 (2026-11-12)

> **이 브랜치의 작업 방향 정본.** 상위 목표를 특정 Controller #996 복구에 종속시키지 않는다.
> 개발/운영 공통 정본은 최신 `main`의 [AGENTS.md](../AGENTS.md), [일반챗 시작](GENERAL_CHAT_START.md), [PC 자동화 표준](PC_AUTOMATION_STANDARD.md), [중앙 인계 계약](AGENT_HANDOFF_CENTRAL_ORCHESTRATOR_V1.md), [공유 자원 수명주기](SHARED_RESOURCE_LIFECYCLE_V1.md)다. 이 문서는 위 정본을 변경하지 않고 #1222 브랜치의 목적·우선순위를 명확히 고정한다.

## 1. 변경하지 않을 근본 목적

**ZGMINI의 여러 일반챗/기능 담당자와 2대 Windows PC가 발생시킨 공통 장애를 단일 공통 대기열로 자동 집계하고, 중앙 처리자가 진단·복구·검증한 결과를 정확한 원담당 작업에 되돌려 원 업무를 재개할 수 있는 반복 가능한 운영 체계를 완성한다.**

정상 업무 흐름은 다음과 같다.

1. **업무 수행:** 운영 PC(`PC`, 운영 Runner `zgmini-pc-01`~`06`)의 기존 승인 `pc-job`/Writer B/유지보수 경로를 각 기능 담당자가 사용한다. 원담당 기능의 수집→계산→저장→게시를 중앙 대기열이 대신하지 않는다.
2. **장애 자동 접수:** 원본 Issue·Run/attempt·정식 bot 결과·JSON/TXT 2/2를 검증하고, 확정된 수리 가능 실패만 기존 GitHub `agent-handoff` Incident로 등록·중복 제거한다. `PASS`, `WAIT_RECORDED`, 청구 전 안전 거부, `STATE_UNKNOWN`은 임의로 복구 사건으로 승격하지 않는다.
3. **분리된 처리 자원:** 공통 대기열 PC(`DESKTOP-N62L0NG`, 전용 Runner `zgmini-handoff-ci-spare-01`, label `zgmini-handoff-ci-isolated`)에서 기존 승인 Workflow의 결과를 검증한다. 원본 운영 PC의 E: 데이터·Controller 소유권을 가져오지 않는다.
4. **중앙 전문 처리:** **단일 중앙 ChatGPT 총괄**이 기존 `agent-handoff` Issue를 조회해 LAST PASS/FIRST FAIL·승인·자원 충돌을 확인하고, 필요시 실제 독립성을 가진 내부 도구/작업을 분담해 공통 문제에 한정한 소스 수정·테스트·PR/CI를 수행한다.
5. **원본에 결과 반환:** 기존 broker 계약으로 원본 Issue에 처리 결과·PR/CI·실제 적용 범위/미완료를 **검증 가능한 영수증으로** 기록한다. 필요한 운영 설치·C급 보안 효과는 별도 Owner 승인과 원담당/단일 효과 담당이 수행한다.
6. **원담당의 작업 재개:** 각 기능 담당자는 자신의 ChatGPT 대화가 실제 열리거나 시작될 때 원본 Issue의 인증된 결과를 확인하고 **마지막 유효 완료 지점에서** 본업을 계속한다. GitHub Issue 댓글만으로 다른 ChatGPT 대화가 자동 깨어나거나 결과를 수신했다고 주장하지 않는다.

**완료 정의:** ‘모든 일반챗이 자동으로 서로를 호출한다’가 아니다. 현재 기술 범위 안에서 **자동 접수 → 중복/오분류 방지 → 중앙 진단·수리 → 원본 결과 반환 → 원담당이 읽을 수 있는 재개 근거**가 안전하고 재사용 가능해야 한다. 원담당 채팅의 실제 수신과 각 기능 운영 배포는 별도 근거로 측정한다.

## 2. 전체 대기열과 #996 복구의 관계

- **상위 과제:** 공통 대기열·중앙 처리·상호 인계 프로세스 정착. #996이 복구되기 전에도 격리 자동 intake/중앙 처리·다른 승인 업무는 가능한 범위에서 정상 진행한다.
- **하위 과제 A — #996:** 기존 운영 PC Controller의 `INTAKE_PAUSED/RUNNER_SET_DRIFT` 복구, 기존 Controller 유지, 원본 요청의 안전한 처리, 정상 `pc-job` 접수 회복. **C급 NO-GO** 및 별도 Owner 승인 대상. 본 PR #1222의 코드/테스트 대부분은 이 하위 과제이며, 코드만으로 공통 대기열 도입이 완료됐다고 말하지 않는다.
- **하위 과제 B — 격리 Writer B intake 5번째 자연 실증:** 실제 유효 수리 가능 실패가 자연 발생할 때 기존 인계→중앙→원본 결과 왕복의 마지막 검증. 의도적으로 장애를 만들지 않는 **DEFERRED/NON_BLOCKING**. #996을 이 검증의 선행 Gate로 삼지 않는다.
- **하위 과제 C — 공유 자원 재계획:** 자원별 `WAITING_SHARED_RESOURCE`와 `RECOVERY_REQUIRED`를 구분하고 원본 잠금·원장·승인 조건이 실제로 해제된 뒤 원담당이 재계획. GitHub 원장만으로 PC lock 해제를 주장하지 않는다.

## 6. 재발 방지 — 왜 목표가 어긋났고 어떻게 고정할 것인가

**확인된 문서 구조 문제:** 브랜치 이름과 PR 제목이 `#996 C recovery`로 시작하고, 8만 자 이상인 기존 복구 계획의 첫·다수 실행 항목이 Windows C/WinPE에 집중되어 있다. 이전 응답에서 이 하위 장벽을 전체 업무의 필수 선행 Gate로 오독했다. 기존 문서 첫머리의 짧은 상위 목표 언급만으로는 실제 실행 순서가 바뀌지 않았다.

**수정 원칙:** (a) 현재 문서를 브랜치의 **첫 번째 목표·우선순위 정본**으로 링크, (b) PR 제목과 본문 서두에서 공통 대기열 최종 목적/#996 하위 범위를 함께 명시, (c) 이슈·계획·보고에서 P0/P1 상위 대기열 운영을 먼저 판단하고, (d) C급 복구는 필요한 승인·독립 영향 범위로 따로 진행한다. 완료된 8/8 실증·A급 읽기 결과·원본 파일/승인 이력은 다시 만들지 않는다.
