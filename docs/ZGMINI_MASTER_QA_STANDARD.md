# ZGMINI 총괄 품질 점검 기준 (Master QA Standard)

- 문서 버전: QA-R1 / 2026-11-05 KST
- 상태: 점검 전용 브랜치 초안. 운영 정책·산식·배포 계약을 변경하거나 자동 실행을 등록하는 문서가 아니다.
- 소유 역할: 총괄 점검 담당자(QA). 기능 수정은 해당 담당자, 공용 설치 조정은 Controller 담당자, 범위 밖 운영 변경 승인은 사용자.
- 적용 대상: `zgmini.kr`의 데스크톱·모바일 웹, **기술 SEO·검색 노출·웹 속도**, 공개 API·D1, PC 수집·계산·게시, Controller·Runner·Scheduler, 관련 GitHub/Cloudflare 배포.
- 기존 정본: 제어 저장소 `main`의 `AGENTS.md`, `docs/PC_AUTOMATION_STANDARD.md`, `docs/GENERAL_CHAT_START.md`, 공개 `zgmini`의 `main/AGENTS.md`. 충돌 시 최신 사용자 승인과 각 업무의 현행 운영 계약을 따른다.

## 1. 목적과 경계

1. 개별 담당자의 완료 주장을 **실제 이용자 화면과 저장·Runtime 증거로 독립 검증**한다.
2. 정상 업무마다 전체 Controller 검사나 전체 회귀를 반복하지 않는다. 변경 영향·관측된 오류에 비례해 표본을 선정하고 기존 유효 증거를 재사용한다.
3. 점검은 기본 읽기 전용이다. QA 결과를 이유로 다른 담당자의 운영 코드·예약·DB·산식·배포·DNS를 임의 수정하거나 일괄 중단하지 않는다.
4. 기능 개발·승인된 독립 작업은 계속한다. 실제 공유 자원 경합만 공용 원장과 승인된 lease 경로로 조정한다.
5. 보안정보·API 키·토큰·원자료 대량본·개인정보는 스크린샷·Issue·로그·커밋에 남기지 않는다.
6. 검사 대상의 정상 작동과 검사 도구 접근성은 별개다. 브라우저·PC 접근 실패는 `AUTOMATION_BLOCKED` 또는 `STATE_UNKNOWN`으로 분리한다.
7. 문서 작성·브랜치 생성·테스트 실행·운영 반영·사용자 화면 정상은 각각 다른 단계로 기록한다.

## 2. 점검 유형과 적용 범위

| 유형 | 시작 조건 | 필수 검사 | 하지 않을 검사 |
| --- | --- | --- | --- |
| 정기 표본 점검 | 사용자 요청 또는 별도 승인된 일정 | 대표 URL의 실제 화면, 관측일/게시일, 변경·실패 표시 | 무관한 전체 PC/DB 재수집 |
| 기능 완료 인수 | 담당자가 완료 증거 제출 | 변경 파일·승인 SHA, 관련 Runtime·D1/API·화면의 실제 결과 | 영향 없는 전체 서비스 재검사 |
| 배포 인수 | 승인된 배포가 발생 | 연결 repo/branch, main SHA, exact 배포, 관련 API/UI | push만 보고 배포 PASS |
| 장애 진단 | 재현 가능한 실패·정확한 오류 | LAST PASS→FIRST FAIL, 영향 자원, 원인·복구 후 동일 조건 RETEST | 무조건 재실행·중복 요청·권한 우회 |
| UX/반응형 감사 | 특정 화면 개선 또는 사용자 보고 | 실제 뷰포트 스크린샷, 주요 조작, 가독성·접근성 | 코드만으로 모바일 PASS |
| 기술 SEO 감사 | 신규 페이지·템플릿 변경, 색인 문제, 사용자 요청 | 실제 HTML/HTTP, canonical/robots/sitemap, 표제·구조화 데이터·내부 링크, 필요 시 GSC | 검색 순위나 노출을 확인 없이 추정 |
| 웹 속도 감사 | 로딩 지연, 중요 페이지 변경, 사용자 요청 | 모바일·PC 필드/실험실 데이터를 구분한 CWV 및 병목 | Lighthouse 한 번으로 전체 속도 PASS |

검사 범위는 사용자가 지정한 기능과 변경 영향에 따라 축소·확대한다. 매번 모든 칸을 검사해야 한다는 전역 Gate를 만들지 않는다.

## 3. 증거 우선순위와 상태 판정

**증거 강도:** 실제 Runtime/브라우저 동작 → API·DB/D1 재조회·checkpoint·정확한 배포 기록 → 사용자 실기기 검증 → 동일 환경 테스트 → source → 문서/추정. 단, 각 계층의 검증은 서로 대체하지 않는다.

- `PASS`: 대상·환경·시각이 명시된 실제 통과 증거가 있다.
- `FAIL`: 동일 조건에서 기대값 위반이나 명시적 Runtime 오류가 재현됐다.
- `PARTIAL`: 확인된 항목은 정상이나 필수 하위 항목 일부가 미확인/실패다. 합격으로 확대하지 않는다.
- `RUNNING`: checkpoint·저장·관측 상태 등 객관적 전진이 있다.
- `STATE_UNKNOWN`: 실행·종료·결과 증거가 부족하다. 실패나 PASS로 치환하지 않는다.
- `NOT_RUN`: 아직 실행하지 않았다.
- `DEFERRED`: 현재 목적과 무관한 후속 개선이다.
- `AUTOMATION_BLOCKED`: 필요한 도구·권한·화면 접근이 제한됐다. 실제 서비스 장애를 의미하지 않는다.
- `RUNTIME_FAILED`: 실제 실행에서 오류가 확인됐다. 오류 범위와 시각을 명시한다.

**심각도:** P0=서비스 전체 중단·실데이터 손상·비밀 노출 위험, P1=핵심 기능 또는 공개 데이터의 중대한 오류, P2=특정 화면/기능의 사용성·표시 오류, P3=경미한 마감·문구. 오래된 관측값은 발표 주기·실제 공급·마지막 저장일과 비교 전까지 자동 P1/FAIL로 분류하지 않는다.

## 4. 시스템·데이터 점검 체크리스트

### 4.1 GitHub/Controller/PC

- [ ] 저장소/작업 브랜치와 최신 `main` SHA, 운영 승인 SHA, 실제 실행·설치 SHA를 별개로 확인한다.
- [ ] Runner 6좌석·Controller·독립 유지보수기 상태는 **이번 업무에 관련될 때만** 최근 실PC 증거로 확인한다. Online 표시만으로 실행 성공을 주장하지 않는다.
- [ ] requestId/chatId 고유성, 동일 요청 중복 방지, A급 허용목록 및 B급 정규 유지보수 경로를 검사한다.
- [ ] Core/Korea 및 실제 등록된 작업의 주기·최근 실행·lease·종료 상태를 업무에 필요한 만큼만 확인한다. 승인 제거된 예약을 임의로 복원하지 않는다.
- [ ] 공유 쓰기·Controller 실제 교체의 경합·drain·원본 해시·복구 계약을 확인한다. 무관한 독립 Reader 작업은 계속한다.
- [ ] 결괏값이 불명확하면 기존 Issue/ledger/checkpoint부터 확인하고 같은 작업을 자동 재실행하지 않는다.

### 4.2 수집→저장→계산→게시

- [ ] Provider의 **관측일**, PC의 **수집/저장 시각**, 계산의 **sourceVersion/sourceStoredAt**, D1의 **게시 시각**, UI의 **표시 날짜**를 분리한다.
- [ ] 원자료는 승인된 PC 저장소에 존재하며 계산은 저장된 입력만 사용한다. 방문자 GET에서 수집·중량 계산을 실행하지 않는다.
- [ ] 신규 공식 관측값·정정값 반영 여부와 마지막 유효 이력 보존을 함께 확인한다. 무조건 오래됐다는 이유로 지연 판정하지 않는다.
- [ ] `0`/`null`/`missing`/`stale`/`PARTIAL`을 구분하고, 오류를 임의 숫자·정상 색상으로 채우지 않는다.
- [ ] D1 게시가 변경 대상이면 정확한 binding/table의 공개 결과를 재조회한다. HTTP 200·envelope READY만으로 payload 완전성을 주장하지 않는다.
- [ ] API 호출량·quota·재시도·공유 lease가 실제 호출자 전체에서 승인 계약을 지키는지 필요한 범위에서 확인한다.

### 4.3 Cloudflare/Production

- [ ] 배포 업무일 때만 GitHub 최신 main → Cloudflare Git Integration → hosted Build/Test → exact Deployment → Production API/UI를 이어 확인한다.
- [ ] 승인되지 않은 Direct Wrangler, Sites, Cron/Queue 계산·수집, DNS·DB 구조 변경은 진행하지 않는다.
- [ ] 배포 성공과 Runtime/D1/UI 성공을 분리하고, 운영 데이터 자동 갱신에 매번 Git push·재배포를 요구하지 않는다.

## 5. 데스크톱·모바일 웹 점검 체크리스트

### 5.1 검사 환경과 증거

대표 뷰포트: 모바일 **375×812**(iPhone 13 mini CSS 기준)·390×844, 태블릿 768×1024, 데스크톱 1366×768·1920×1080. 모든 업무에 전부 강제하지 않고 변경 영향이 있는 화면 크기를 선택한다. 필요할 때 320px 너비의 재배치도 별도 확인한다.

- [ ] 화면의 실제 너비·높이, 브라우저/기기, URL, KST 시각, 로그인 여부, 선택한 기간/필터를 기록한다.
- [ ] 페이지 로딩 완료 후 정확한 화면을 캡처한다. 로딩/오류/빈 화면은 완료 화면과 구분한다.
- [ ] 브라우저 확대/축소·데스크톱 창만으로 모바일 실기기 성공을 주장하지 않는다. 모바일 뷰포트 제어가 불가능하면 `NOT_RUN` 또는 `AUTOMATION_BLOCKED`.
- [ ] 화면·DOM·키보드/터치 행동 증거를 구분한다. 스크린샷만으로 WCAG 전체 준수나 API 정확성을 확정하지 않는다.

### 5.2 모든 대표 페이지의 공통 항목

- [ ] 메뉴·뒤로 가기·내부 링크·주요 버튼·탭·검색·필터·모달 열기/닫기가 실제 동작한다.
- [ ] 모바일에서 가로 넘침, 표의 한두 글자 강제 줄바꿈, 카드 잘림, 겹침, 스크롤 불능, 고정 요소의 내용 가림이 없다.
- [ ] 숫자·단위·부호·색상·상승/하락 방향·결측·관측일·게시일이 API/저장 계약과 맞는다.
- [ ] 그래프의 시작/끝·마지막 점·실제 데이터 길이·기간 선택·축 라벨·선 두께·색상이 올바르다. 부분 기간을 전체 기간처럼 늘리거나 0으로 채우지 않는다.
- [ ] 색만으로 의미를 구분하지 않으며 상태 문구·범례·접근 가능한 이름이 있다.
- [ ] 작은 글씨·대비·키보드 포커스·탭 순서·터치 대상·확대 시 재배치를 확인한다. 불명확하면 별도 접근성 위험으로 표시한다.
- [ ] 로딩·오류·빈 데이터·stale 상태가 이용자에게 오해 없이 설명된다.
- [ ] 콘솔/네트워크 오류는 볼 수 있을 때 기록하되, 검사 도구가 제공하지 않는 로그를 확인했다고 주장하지 않는다.

### 5.4 기술 SEO 점검

SEO는 **검색 가능성·콘텐츠 이해·페이지 품질**을 검사하는 별도 품질 영역이다. SEO 점검 스킬·공식 검색엔진 도구가 적합하면 활용하되, 무료 공식 도구와 유효한 기존 증거를 우선한다. 단순 문서 갱신만으로 전체 크롤링을 자동 시작하지 않는다.

- [ ] 대표 템플릿의 실제 응답 코드(200/3xx/4xx/5xx), 리디렉션, 접근 가능 URL과 모바일에서 읽히는 본문을 확인한다.
- [ ] `robots.txt`, sitemap 위치와 대상 URL, `noindex`/robots 지시, canonical `link`를 실제 HTML/헤더에서 확인한다. robots 차단과 색인 제외를 혼동하지 않는다.
- [ ] canonical 선언과 **Google이 선택한 canonical**은 별개다. 실제 색인 상태·색인 제외 이유는 Google Search Console/URL 검사 증거가 있을 때만 확정한다.
- [ ] 페이지 목적에 맞는 고유 `<title>`·meta description·H1·H2~구조, 내부 링크·앵커 의미, 이미지 대체 텍스트, 중복/빈 메타데이터를 점검한다.
- [ ] 구조화 데이터(JSON-LD 등)가 실제 페이지 내용과 일치하고 적용 타입 및 필수 필드가 유효한지 확인한다. 마크업만으로 Google 검색 결과의 리치 노출을 보장하지 않는다.
- [ ] SSR/JS 렌더링에 따라 검색엔진이 본문·링크·필수 데이터에 접근할 수 있는지 필요한 페이지에서 확인한다. 단순 소스에 비어 있다는 이유만으로 실제 렌더링 실패로 판정하지 않는다.
- [ ] 금융 정보의 날짜·출처·해석 문구·정확성을 확인한다. 관측일과 게시일을 구분하고, stale 값을 최신처럼 표현하지 않는다.
- [ ] 실제 검색 유입·쿼리·노출·클릭·색인 상태는 기간·속성·URL이 일치하는 Search Console 자료가 있을 때만 보고한다. 표본 순위·검색 화면 위치로 전체 순위를 단정하지 않는다.
- [ ] 링크 장애는 대상 URL을 직접 재확인하고, 일시적 크롤러 차단을 실제 404로 보고하지 않는다. 표본만 검사했다면 검사한 URL 수와 미검사 범위를 밝힌다.

**우선순위 예시:** 의도치 않은 전체 `noindex`/잘못된 canonical/핵심 URL 5xx는 높은 영향 후보, 중복 제목·빈 alt·약한 내부 링크는 확인된 영향에 맞게 분류한다. SEO 개선 권고가 즉시 운영 수정·게시 승인이라는 뜻은 아니다.

### 5.5 웹사이트 속도·성능 점검

**Google Core Web Vitals의 실사용자 기준:** 모바일과 데스크톱을 **각각 분리**하고, 가능할 때 최근 현장 데이터(예: CrUX)의 **75번째 백분위수**를 확인한다.

| 핵심 지표 | 좋음(Good) 기준 | 무엇을 보는가 |
| --- | --- | --- |
| LCP | **2.5초 이하** | 화면의 주요 콘텐츠 표시 속도 |
| INP | **200ms 이하** | 클릭·터치·키 입력에 대한 반응성 |
| CLS | **0.1 이하** | 예기치 않은 화면 이동 |

참조: [web.dev Core Web Vitals 기준](https://web.dev/articles/defining-core-web-vitals-thresholds). 이는 Google의 공개 분류 기준이며, ZGMINI 운영 계약에 새로운 자동 차단 Gate를 추가한 것은 아니다.

- [ ] PageSpeed Insights/CrUX/Search Console의 **실사용자 필드 데이터**와 Lighthouse·브라우저 측정의 **실험실 데이터**를 구분한다. 표본 부족 시 `NO_FIELD_DATA`로 기록하고 임의 PASS/FAIL을 하지 않는다.
- [ ] 대표 URL(대시보드, 미국 공탐 상세, 경제지표 상세, 테마 공탐, 시장 캘린더)을 화면 유형별로 선택한다. 모든 경로에 동일한 장시간 측정을 강제하지 않는다.
- [ ] 모바일·PC를 동일한 URL·기간·조건으로 비교하고 네트워크·기기 성능·캐시 상태·측정 시각·도구 버전을 기록한다.
- [ ] 초기 HTML/TTFB, FCP, LCP, INP(필드), CLS, Lighthouse TBT, JS 실행·이미지·폰트·CSS 전송량, 캐시/압축, 3rd-party 스크립트를 필요 범위에서 분석한다.
- [ ] 데이터 로딩 스켈레톤이나 지연 표시가 있으면 **첫 화면이 보이는 시각**과 **실제 점수/차트/표가 준비되는 시각**을 구분한다. HTTP 200이나 로더 표시로 기능 준비 PASS를 주장하지 않는다.
- [ ] 기간 전환·필터·차트 도구 설명의 상호작용 지연, 큰 표 스크롤 및 모바일 저사양 환경의 끊김을 확인한다.
- [ ] 원인 확정 전 이미지 삭제·차트 생략·지표 숨기기·산식 수정·캐시 TTL 변경 같은 품질 희생형 최적화를 수행하지 않는다. 개선 전후 동일 조건 재측정과 기능 회귀 검증을 요구한다.
- [ ] Lighthouse Performance 점수는 **진단 신호**로 사용한다. 점수 90 이상 여부 하나를 실사용자 CWV PASS나 검색 순위 향상으로 대체하지 않는다.

**보고:** URL/기기별 CWV 값·출처·측정 기간, 실험실 반복 측정의 범위, 원인(확정/추정), 영향받는 UI, 최소 변경 후보, 관련 담당자, 수정 후 RETEST를 남긴다.

## 6. 검사 기록 양식

각 문제는 한 건의 재현 가능한 기록으로 남긴다. 비밀정보·전체 원자료는 기록하지 않는다.

```text
QA ID:
검사 목적 / 범위:
담당 / 검사 유형:
KST 검사 시작·종료 / 진행률(완료한 필수 항목 수 ÷ 계획 필수 항목 수):
저장소 / 기준 브랜치·SHA / 작업 브랜치·SHA:
운영 승인 SHA / 실제 실행·배포 SHA (관련될 때만):
환경: URL, PC/모바일 뷰포트, 브라우저, 선택 기간·필터
SEO(해당 시): HTTP/robots/canonical/title/description/H1/structured data/sitemap, GSC 근거
속도(해당 시): 모바일·PC, CrUX·Lighthouse 구분, LCP/INP/CLS, 수집 기간·장치 조건
관측일 / PC sourceStoredAt / D1 게시일 / UI 표시일 (확인한 항목만):
기대값과 근거:
실제값 / 수행한 조작:
증거: 실제 스크린샷·API/D1 readback·로그·Issue·커밋 링크
판정: PASS / FAIL / PARTIAL / RUNNING / STATE_UNKNOWN / NOT_RUN / DEFERRED
문제 유형 / 심각도 / 영향 범위:
LAST PASS / FIRST FAIL / exact error:
원인(확정 또는 추정 구분) / 부작용:
최소 수정 방안 / 담당:
RETEST 조건과 결과:
NEXT: 담당, 입력, 경로, 통과 조건 중 한 가지 필수 실행
```

진행률은 **정한 필수 검사항목의 확인 비율**로만 표시한다. 3/5 완료는 60%이며 실제 서비스 건강 점수가 아니다. `PASS` 근거가 없는 항목은 자동 완성 처리하지 않는다.

## 7. 총괄 점검 운영 방식

1. **착수:** 현재 요청·변경 파일·기존 검증·적용 범위를 식별하고 필수 검사 항목과 시작 진행률을 정의한다.
2. **검사:** 독립적이고 무료인 도구를 우선한다. 실제 브라우저 화면, GitHub/Cloudflare 공식 기록, 승인된 PC A급 읽기 경로, 관련 UX·접근성 전문 도구를 필요한 만큼 사용한다. 도구 미연결은 관측 한계로 기록한다.
3. **판정:** PASS/FAIL/미검증을 나누고 P0/P1만 즉시 대응을 권고한다. 다른 담당자와 충돌할 수 있는 변경은 공용 조정 경로로 보낸다.
4. **인수:** 수정 담당자가 제출한 변경의 실제 영향 부분만 RETEST한다. 잘못된 기존 검사를 약화하거나 동일 증거를 새 성과로 포장하지 않는다.
5. **보고:** 이번 수행, 확인된 결과, 중요한 문제, 다음 **필수 실행 하나**만 한국어로 보고한다. 작업 브랜치·반영 SHA·실제 실행/배포 여부를 반드시 명시한다.

## 8. 전문 플러그인·도구 선정 원칙

**원칙:** 가능한 한 이미 연결된 무료 도구로 근거를 모으고, 한 문제에 모든 플러그인을 호출하지 않는다. 아래는 역할 분담이지 설치·계정 연결·자동 실행 승인 또는 데이터 접근 성공의 선언이 아니다.

| 우선도 | 도구/전문 기능 | 사용 시점과 검증 책임 | 한계·보호 |
| --- | --- | --- | --- |
| 상시 핵심 | **GitHub 연결 도구** | repo/main·작업 브랜치·exact SHA·PR diff·Actions·Issue 증거 | CI/PASS를 PC 설치·Cloudflare Runtime PASS로 치환 금지 |
| 웹 검사 핵심 | **Browser / 허용된 Computer Use** | 실제 PC 웹의 탐색·필터·차트·콘솔·로딩과 모바일 뷰포트 검증 | 사용자의 브라우저 연결 여부·뷰포트 제어를 확인. 불가능하면 모바일 미검증 |
| UX 전문 | **Product Design의 Audit** | 스크린샷 순서별 사용성·레이아웃·접근성 위험 평가 | 실제 캡처가 없는 화면을 감사한 것으로 보고하지 않음. WCAG 전체 준수 보장 금지 |
| SEO 성과 핵심 | **Windsor.ai → Google Search Console** | `sc-domain:zgmini.kr` 등 실제 연결된 속성의 노출·클릭·CTR·검색어·색인 지표를 읽을 때 | 계정 연결과 해당 기간의 정상 조회를 구분. 속성·기간 불일치 자료로 ZGMINI 성과 주장 금지 |
| 운영 분석 보조 | **PostHog** | 실제 사용자 흐름·오류·성능 이벤트의 이미 수집된 자료가 필요할 때 | 데이터 없음은 `NO_RUNTIME_EVIDENCE`. Cloudflare Runtime/D1 증거보다 우선하지 않음 |
| SEO 기술 심화 | **Firecrawl의 SEO Audit** | 실제 HTML·meta·canonical·JSON-LD·내부 링크의 복수 페이지 확인이 무료 직접 조회만으로 부족할 때 | 크레딧·quota·비용 상태 확인 후 필요한 URL만. 일반 검색·공식문서로 충분하면 호출하지 않음 |
| 디자인 비교 조건부 | **Figma** | 실제 Figma 원본·토큰·화면이 있는 UI 변경에서 디자인 대조가 필요할 때 | 원본이 없는데 임의 디자인 기준을 새로 만들지 않음 |
| 기술 검증 조건부 | **Context7** | React/Next/Vinext/Cloudflare/라이브러리의 버전별 API·공식 문서와 구현을 대조할 때 | 실제 설치 버전·소스가 확인된 후 조회. 문서만으로 Runtime PASS 금지 |
| 협업 추적 조건부 | **Linear** | 여러 담당자·단계·의존성이 얽힌 QA 이슈를 별도로 추적할 필요가 있을 때 | 공통 GitHub #68 원장이나 개별 Issue와 중복 상태·상충 지시를 만들지 않음 |
| 대규모 결과 정리 조건부 | **Google Drive / Sheets** | 장기 QA 결과·URL별 성능·SEO 이력을 사용자가 협업 문서로 원할 때 | GitHub QA 브랜치가 정본. 비밀 로그·PC 원자료·인증정보를 외부 문서로 복제하지 않음 |

**플러그인 없는 공식 도구도 우선 사용:** 웹 속도는 PageSpeed Insights/CrUX의 필드 자료와 Lighthouse 실험실 자료를 역할에 맞게 사용한다. 배포·D1·Worker는 관련 Cloudflare 공식 조회/API 및 이미 유효한 증거를 우선한다. 보안은 GitHub의 활성화된 의존성 경고·코드 분석·secret scanning 및 관련 공식 보안 검사를 **접근 가능한 범위에서** 읽기 전용으로 확인한다. 기능 미활성·접근 제한은 검사 미실시로 표시한다. Google Search Console 자체나 속도 측정을 위해 신규 유료 플러그인 설치를 기본 전제로 삼지 않는다.

**기본 실행 순서:** ① 기존 증거·GitHub 영향 확인 → ② 필요한 실제 브라우저/PC/API 검사 → ③ UX 또는 SEO 전문 분석 → ④ 성능·사용자 행동 보조 증거 → ⑤ 문제별 판정·담당자 전달·동일 조건 RETEST. 대상과 목적이 명확하면 해당 단계만 선택한다.

**도입 보류 후보:** **Ahrefs**는 백링크·경쟁 키워드·검색 가시성이 현재 Search Console로 해결되지 않는 과제로 확인될 때만 제안한다. **Datadog**은 기존 Cloudflare/PostHog가 제공하지 못하는 실제 로그·분산 추적·RUM이 필수일 때만 검토한다. 둘 다 현재 미설치이며 계정·비용·계측 범위 확인 없이 설치나 데이터 수집을 시작하지 않는다.

**사용 제외 기본값:** ZGMINI Production에 OpenAI Sites 사용 금지. Supabase를 운영 DB 대체로 쓰지 않음. TinyFish는 무료 수단으로 해결 불가능하고 사용자가 명시 승인한 경우 외 기본 사용 금지. 새 중복 관측 플랫폼과 지속과금 리소스는 필요·비용·승인이 입증되기 전 추가하지 않는다. 플러그인의 가용성·연결·요금은 작업 시작 시 필요한 항목만 확인한다.

## 9. 이 문서 자체의 완료 조건

- [ ] 기존 공통 정본과 모순 없이 읽기 전용 QA 범위·상태/심각도·PC/데이터/UI·SEO·웹 속도 검사표·보고 템플릿이 존재한다.
- [ ] 이 파일이 **전용 QA 브랜치**에만 반영되고 exact commit SHA와 원격 내용을 재조회했다.
- [ ] `main` 병합, PC 작업/수집, DB/D1 쓰기, Cloudflare 배포, DNS 변경을 하지 않았다.
- [ ] 실제 신규 UX 또는 운영 PASS는 **별도 검사 증거가 있는 항목만** 주장한다.

다음 실행은 사용자가 지정하는 최초 인수 대상의 체크리스트를 추려 실제 데스크톱·모바일 화면과 관련 Runtime 증거를 수집하는 것이다. 정기 자동 점검은 별도 일정 승인·지원 경로 없이 시작하지 않는다.
