# ZGMINI 총괄 품질 점검 기준 (Master QA Standard)

- 문서 버전: QA-R1 / 2026-11-05 KST
- 상태: 점검 전용 브랜치 초안. 운영 정책·산식·배포 계약을 변경하거나 자동 실행을 등록하는 문서가 아니다.
- 소유 역할: 총괄 점검 담당자(QA). 기능 수정은 해당 담당자, 공용 설치 조정은 Controller 담당자, 범위 밖 운영 변경 승인은 사용자.
- 적용 대상: `zgmini.kr`의 데스크톱·모바일 웹, 공개 API·D1, PC 수집·계산·게시, Controller·Runner·Scheduler, 관련 GitHub/Cloudflare 배포.
- 기존 정본: 제어 저장소 `main`의 `AGENTS.md`, `docs/PC_AUTOMATION_STANDARD.md`, `docs/GENERAL_CHAT_START.md`, 공개 `zgmini`의 `main/AGENTS.md`. 충돌 시 최신 사용자 승인과 각 업무의 현행 운영 계약을 따른다.

## 1. 목적과 경계

1. 개별 담당자의 완료 주장을 **실제 이용자 화면과 저장·Runtime 증거로 독립 검증**한다.
2. 정상 업무마다 전체 Controller 검사나 전체 회귀를 반복하지 않는다. 변경 영향·관측된 오류에 비례해 표본을 선정하고 기존 유효 증거를 재사용한다.
3. 점검은 기본 읽기 전용이다. QA 결과를 이유로 다른 담당자의 운영 코드·예약·DB·산식·배포·DNS를 임의 수정하거나 일괄 중단하지 않는다.
4. 기능 개발·승인된 독립 작업은 계속한다. 실제 공유 자원 경합만 공용 원장과 승인된 lease 경로로 조정한다.
5. 보안정보·API 키·토큰·원자료 대량본·개인정보는 스크린샷·Issue·로그·커밋에 남기지 않는다.
6. 검사 대상의 정상 작동과 검사 도구 접근성은 별개다. 브라우저·PC 접근 실패는 `AUTOMATION_BLOCKED` 또는 `STATE_UNKNOWN`으로 분리한다.
7. 문서 작성·브랜치 생성·테스트 실행·운영 반영·사용자 화면 정상은 각각 다른 단계로 기록한다.

## 2. 점검 유형과 적용 범위

| 유형 | 시작 조건 | 필수 검사 | 하지 않을 검사 |
| --- | --- | --- | --- |
| 정기 표본 점검 | 사용자 요청 또는 별도 승인된 일정 | 대표 URL의 실제 화면, 관측일/게시일, 변경·실패 표시 | 무관한 전체 PC/DB 재수집 |
| 기능 완료 인수 | 담당자가 완료 증거 제출 | 변경 파일·승인 SHA, 관련 Runtime·D1/API·화면의 실제 결과 | 영향 없는 전체 서비스 재검사 |
| 배포 인수 | 승인된 배포가 발생 | 연결 repo/branch, main SHA, exact 배포, 관련 API/UI | push만 보고 배포 PASS |
| 장애 진단 | 재현 가능한 실패·정확한 오류 | LAST PASS→FIRST FAIL, 영향 자원, 원인·복구 후 동일 조건 RETEST | 무조건 재실행·중복 요청·권한 우회 |
| UX/반응형 감사 | 특정 화면 개선 또는 사용자 보고 | 실제 뷰포트 스크린샷, 주요 조작, 가독성·접근성 | 코드만으로 모바일 PASS |

검사 범위는 사용자가 지정한 기능과 변경 영향에 따라 축소·확대한다. 매번 모든 칸을 검사해야 한다는 전역 Gate를 만들지 않는다.

## 3. 증거 우선순위와 상태 판정

**증거 강도:** 실제 Runtime/브라우저 동작 → API·DB/D1 재조회·checkpoint·정확한 배포 기록 → 사용자 실기기 검증 → 동일 환경 테스트 → source → 문서/추정. 단, 각 계층의 검증은 서로 대체하지 않는다.

- `PASS`: 대상·환경·시각이 명시된 실제 통과 증거가 있다.
- `FAIL`: 동일 조건에서 기대값 위반이나 명시적 Runtime 오류가 재현됐다.
- `PARTIAL`: 확인된 항목은 정상이나 필수 하위 항목 일부가 미확인/실패다. 합격으로 확대하지 않는다.
- `RUNNING`: checkpoint·저장·관측 상태 등 객관적 전진이 있다.
- `STATE_UNKNOWN`: 실행·종료·결과 증거가 부족하다. 실패나 PASS로 치환하지 않는다.
- `NOT_RUN`: 아직 실행하지 않았다.
- `DEFERRED`: 현재 목적과 무관한 후속 개선이다.
- `AUTOMATION_BLOCKED`: 필요한 도구·권한·화면 접근이 제한됐다. 실제 서비스 장애를 의미하지 않는다.
- `RUNTIME_FAILED`: 실제 실행에서 오류가 확인됐다. 오류 범위와 시각을 명시한다.

**심각도:** P0=서비스 전체 중단·실데이터 손상·비밀 노출 위험, P1=핵심 기능 또는 공개 데이터의 중대한 오류, P2=특정 화면/기능의 사용성·표시 오류, P3=경미한 마감·문구. 오래된 관측값은 발표 주기·실제 공급·마지막 저장일과 비교 전까지 자동 P1/FAIL로 분류하지 않는다.

## 4. 시스템·데이터 점검 체크리스트

### 4.1 GitHub/Controller/PC

- [ ] 저장소/작업 브랜치와 최신 `main` SHA, 운영 승인 SHA, 실제 실행·설치 SHA를 별개로 확인한다.
- [ ] Runner 6좌석·Controller·독립 유지보수기 상태는 **이번 업무에 관련될 때만** 최근 실PC 증거로 확인한다. Online 표시만으로 실행 성공을 주장하지 않는다.
- [ ] requestId/chatId 고유성, 동일 요청 중복 방지, A급 허용목록 및 B급 정규 유지보수 경로를 검사한다.
- [ ] Core/Korea 및 실제 등록된 작업의 주기·최근 실행·lease·종료 상태를 업무에 필요한 만큼만 확인한다. 승인 제거된 예약을 임의로 복원하지 않는다.
- [ ] 공유 쓰기·Controller 실제 교체의 경합·drain·원본 해시·복구 계약을 확인한다. 무관한 독립 Reader 작업은 계속한다.
- [ ] 결괏값이 불명확하면 기존 Issue/ledger/checkpoint부터 확인하고 같은 작업을 자동 재실행하지 않는다.

### 4.2 수집→저장→계산→게시

- [ ] Provider의 **관측일**, PC의 **수집/저장 시각**, 계산의 **sourceVersion/sourceStoredAt**, D1의 **게시 시각**, UI의 **표시 날짜**를 분리한다.
- [ ] 원자료는 승인된 PC 저장소에 존재하며 계산은 저장된 입력만 사용한다. 방문자 GET에서 수집·중량 계산을 실행하지 않는다.
- [ ] 신규 공식 관측값·정정값 반영 여부와 마지막 유효 이력 보존을 함께 확인한다. 무조건 오래됐다는 이유로 지연 판정하지 않는다.
- [ ] `0`/`null`/`missing`/`stale`/`PARTIAL`을 구분하고, 오류를 임의 숫자·정상 색상으로 채우지 않는다.
- [ ] D1 게시가 변경 대상이면 정확한 binding/table의 공개 결과를 재조회한다. HTTP 200·envelope READY만으로 payload 완전성을 주장하지 않는다.
- [ ] API 호출량·quota·재시도·공유 lease가 실제 호출자 전체에서 승인 계약을 지키는지 필요한 범위에서 확인한다.

### 4.3 Cloudflare/Production

- [ ] 배포 업무일 때만 GitHub 최신 main → Cloudflare Git Integration → hosted Build/Test → exact Deployment → Production API/UI를 이어 확인한다.
- [ ] 승인되지 않은 Direct Wrangler, Sites, Cron/Queue 계산·수집, DNS·DB 구조 변경은 진행하지 않는다.
- [ ] 배포 성공과 Runtime/D1/UI 성공을 분리하고, 운영 데이터 자동 갱신에 매번 Git push·재배포를 요구하지 않는다.

## 5. 데스크톱·모바일 웹 점검 체크리스트

### 5.1 검사 환경과 증거

대표 뷰포트: 모바일 **375×812**(iPhone 13 mini CSS 기준)·390×844, 태블릿 768×1024, 데스크톱 1366×768·1920×1080. 모든 업무에 전부 강제하지 않고 변경 영향이 있는 화면 크기를 선택한다. 필요할 때 320px 너비의 재배치도 별도 확인한다.

- [ ] 화면의 실제 너비·높이, 브라우저/기기, URL, KST 시각, 로그인 여부, 선택한 기간/필터를 기록한다.
- [ ] 페이지 로딩 완료 후 정확한 화면을 캡처한다. 로딩/오류/빈 화면은 완료 화면과 구분한다.
- [ ] 브라우저 확대/축소·데스크톱 창만으로 모바일 실기기 성공을 주장하지 않는다. 모바일 뷰포트 제어가 불가능하면 `NOT_RUN` 또는 `AUTOMATION_BLOCKED`.
- [ ] 화면·DOM·키보드/터치 행동 증거를 구분한다. 스크린샷만으로 WCAG 전체 준수나 API 정확성을 확정하지 않는다.

### 5.2 모든 대표 페이지의 공통 항목

- [ ] 메뉴·뒤로 가기·내부 링크·주요 버튼·탭·검색·필터·모달 열기/닫기가 실제 동작한다.
- [ ] 모바일에서 가로 넘침, 표의 한두 글자 강제 줄바꿈, 카드 잘림, 겹침, 스크롤 불능, 고정 요소의 내용 가림이 없다.
- [ ] 숫자·단위·부호·색상·상승/하락 방향·결측·관측일·게시일이 API/저장 계약과 맞는다.
- [ ] 그래프의 시작/끝·마지막 점·실제 데이터 길이·기간 선택·축 라벨·선 두께·색상이 올바르다. 부분 기간을 전체 기간처럼 늘리거나 0으로 채우지 않는다.
- [ ] 색만으로 의미를 구분하지 않으며 상태 문구·범례·접근 가능한 이름이 있다.
- [ ] 작은 글씨·대비·키보드 포커스·탭 순서·터치 대상·확대 시 재배치를 확인한다. 불명확하면 별도 접근성 위험으로 표시한다.
- [ ] 로딩·오류·빈 데이터·stale 상태가 이용자에게 오해 없이 설명된다.
- [ ] 콘솔/네트워크 오류는 볼 수 있을 때 기록하되, 검사 도구가 제공하지 않는 로그를 확인했다고 주장하지 않는다.

### 5.3 화면별 최소 인수 표

| 화면 | 최소 사용자 동작 | 특히 확인할 값 |
| --- | --- | --- |
| 메인 대시보드 `/` | 공탐 기간 전환, 상세페이지 이동, 도움말 | 미국/한국 점수·등락비율 기준일·종합 점수·8대 위험·미니차트 |

| 경제지표 목록/상세 | 물가·고용 등 대표 상세, 표/차트 | 이전/현재/기준/판단·단위·원자료와 평가점수 구분 |

| 테마 공포·탐욕 | 분류/검색/비교 체크·기간 | 공개 건수·순위·최종 관측일·비교 차트 |
| 시장 캘린더 | 날짜/필터/이벤트 상세 | KST·발표 예정/확정·중요도·중복·상태 |
| 아웃브레이크 | 카드→상세·최근 14일 차트 | 실제/예시/추정 구분·저장/게시일·확정/잠정 |

기능이 개발 중이라면 `NOT_RUN`/기능 상태를 기록하고, 별도 승인 없는 완성 조건을 임의로 추가하지 않는다.

## 6. 검사 기록 양식

각 문제는 한 건의 재현 가능한 기록으로 남긴다. 비밀정보·전체 원자료는 기록하지 않는다.

```text
QA ID:
검사 목적 / 범위:
담당 / 검사 유형:
KST 검사 시작·종료 / 진행률(완료한 필수 항목 수 ÷ 계획 필수 항목 수):
저장소 / 기준 브랜치·SHA / 작업 브랜치·SHA:
운영 승인 SHA / 실제 실행·배포 SHA (관련될 때만):
환경: URL, PC/모바일 뷰포트, 브라우저, 선택 기간·필터
관측일 / PC sourceStoredAt / D1 게시일 / UI 표시일 (확인한 항목만):
기대값과 근거:
실제값 / 수행한 조작:
증거: 실제 스크린샷·API/D1 readback·로그·Issue·커밋 링크
판정: PASS / FAIL / PARTIAL / RUNNING / STATE_UNKNOWN / NOT_RUN / DEFERRED
문제 유형 / 심각도 / 영향 범위:
LAST PASS / FIRST FAIL / exact error:
원인(확정 또는 추정 구분) / 부작용:
최소 수정 방안 / 담당:
RETEST 조건과 결과:
NEXT: 담당, 입력, 경로, 통과 조건 중 한 가지 필수 실행
```

진행률은 **정한 필수 검사항목의 확인 비율**로만 표시한다. 3/5 완료는 60%이며 실제 서비스 건강 점수가 아니다. `PASS` 근거가 없는 항목은 자동 완성 처리하지 않는다.

## 7. 총괄 점검 운영 방식

1. **착수:** 현재 요청·변경 파일·기존 검증·적용 범위를 식별하고 필수 검사 항목과 시작 진행률을 정의한다.
2. **검사:** 독립적이고 무료인 도구를 우선한다. 실제 브라우저 화면, GitHub/Cloudflare 공식 기록, 승인된 PC A급 읽기 경로, 관련 UX·접근성 전문 도구를 필요한 만큼 사용한다. 도구 미연결은 관측 한계로 기록한다.
3. **판정:** PASS/FAIL/미검증을 나누고 P0/P1만 즉시 대응을 권고한다. 다른 담당자와 충돌할 수 있는 변경은 공용 조정 경로로 보낸다.
4. **인수:** 수정 담당자가 제출한 변경의 실제 영향 부분만 RETEST한다. 잘못된 기존 검사를 약화하거나 동일 증거를 새 성과로 포장하지 않는다.
5. **보고:** 이번 수행, 확인된 결과, 중요한 문제, 다음 **필수 실행 하나**만 한국어로 보고한다. 작업 브랜치·반영 SHA·실제 실행/배포 여부를 반드시 명시한다.

## 8. 이 문서 자체의 완료 조건

- [ ] 기존 공통 정본과 모순 없이 읽기 전용 QA 범위·상태/심각도·PC/데이터/UI 검사표·보고 템플릿이 존재한다.
- [ ] 이 파일이 **전용 QA 브랜치**에만 반영되고 exact commit SHA와 원격 내용을 재조회했다.
- [ ] `main` 병합, PC 작업/수집, DB/D1 쓰기, Cloudflare 배포, DNS 변경을 하지 않았다.
- [ ] 실제 신규 UX 또는 운영 PASS는 **별도 검사 증거가 있는 항목만** 주장한다.
