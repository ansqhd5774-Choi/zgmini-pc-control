# ZGMINI — 일반챗·CMD·PC Runner 공통 작업 지침

2026-11-03 개정 정본 — 상시 승인·현재 상태 조회·접수 실패 분류·공용 복구/재개·작업 전 학습 절차 통합. 이전의 동일 목적 지시문을 대체하며, 현재 승인된 작업을 처음부터 다시 시작하라는 뜻이 아니다.

## 1. 목적과 정본

승인된 작업을 일반챗의 GitHub 요청 → PC 실행 → TXT·JSON·댓글 회수 → 분석 → 후속 작업까지 처리한다. 사용자에게 매번 CMD 실행과 파일 전달을 요구하지 않는다.

제어 저장소는 `ansqhd5774-Choi/zgmini-pc-control`, 기준 브랜치는 `main`이다. 먼저 `AGENTS.md`, `README.md`, `docs/GENERAL_CHAT_START.md`를 읽는다. 연결 장애는 `docs/RUNNER_RECOVERY.md`, 업데이트는 `docs/CONTROLLER_AUTO_UPDATE.md`, 여러 작업의 공용 적용은 `docs/CONTROLLER_APPLY_QUEUE.md`를 필요한 범위에서 참조한다.

GitHub 도구의 실제 읽기·쓰기 접근 가능성을 확인한다. 도구 미연결을 PC 장애로 판단하거나, Runner 설치만으로 새 대화에 도구 권한이 생겼다고 가정하지 않는다.

작업 전 전달용 요약은 [GENERAL_CHAT_PREWORK.md](GENERAL_CHAT_PREWORK.md), 현재 상태 조회와 접수 실패 분류는 [AUTOMATION_STATUS_AND_ADMISSION.md](AUTOMATION_STATUS_AND_ADMISSION.md)를 따른다. Runtime 건강·현재 잠금·과거 원장·요청 도구 권한을 별도 상태로 판단한다. 외부 도구 안전 검사 거부는 원문 사유를 확보하며 차단 행동을 다른 도구로 우회하지 않는다.

현재 작업의 목적·전용 브랜치·승인 범위와 유효한 완료 증거를 유지한다. 과거 SHA·PID·설치 상태를 현재값으로 가정하지 않는다. 제어 저장소 최신 SHA, 실제 Controller 설치 SHA, 유지보수기 source SHA, 검사 대상 source SHA를 구분한다.

업무 시작 또는 담당 인계 때 작업 전 요약을 적용하고, 장시간 작업의 재개·실제 오류·source/설치 변경 때 관련 정본과 상태만 다시 확인한다. 매번 전체 테스트·전체 문서를 반복 조사하지 않는다. 사용자가 붙여넣은 이전 사본에 최신 보완이 없으면 GitHub 정본의 관련 변경을 적용한다.

## 2. 일반 작업 실행

### 실행 전 현재 상태 판정

현재 설치된 기능·입력·실행 경로와 업무 승인 범위를 먼저 대조한다. 설정·기존 adapter로 가능한 일을 새 Controller 설치나 기능별 CMD 생성으로 확대하지 않는다. 새 실행 코드가 실제로 필요할 때만 최소 모듈 등록·검증·갱신을 수행한다.

지원되는 PC 수단에서 `tools/automation-status.mjs`를 읽기 전용으로 조회할 수 있으면 현재 설치 SHA·활성 install lease·fresh Supervisor·Runner·설치 operation을 함께 확인한다. 이 도구를 설치된 pc-job 허용목록에 자동 포함됐다고 가정하지 않는다. `observedAt`과 `freshnessSeconds`를 확인하고, 원장에 남은 과거 RECOVERY_REQUIRED와 현재 활성 잠금을 분리한다. 현재 잠금 부재는 과거 복구나 새 설치의 성공 증거를 대신하지 않는다.

### 요청과 결과

실제 설치된 허용목록에서 작업을 선택하고, 현재 schema에 맞는 `pc-job` Issue를 한 번 생성한다. 대화별 `chatId`와 요청별 `requestId`는 해당 계약의 정확한 UUID 형식으로 만들고 제출 전에 검증한다. 임의 문자열을 예시와 혼용하지 않는다.

결과의 `status`, `code`, `lastPass`, `firstFail`, 실제 실행 SHA 및 TXT·JSON·댓글을 직접 확인한다. Actions 성공이나 HTTP 200만으로 실제 작업 성공을 대신하지 않는다.

접수 단계는 다음과 같이 분류하고 실제로 막힌 단계만 처리한다.

| 단계 | 다음 행동 |
|---|---|
| 도구 미연결·권한 부족 | 해당 접근 범위만 안내하고 PC 장애로 판정하지 않음 |
| schema 오류 | 실제 인수 계약을 수정. 생성 여부 불명확 시 기존 requestId부터 조회 |
| 도구 안전 검사 거부 | 차단 행동·비민감 거부 원문·사유를 기록. 같은 행동을 다른 도구/명령으로 우회하지 않음 |
| 생성 timeout·응답 유실 | 기존 Issue·requestId를 조회해 생성 여부 확정. 중복 제출 금지 |
| Issue 존재·PC 미접수 | receiver·활성 잠금·요청 원장 확인 |
| PC 실행 실패 | 실제 실패 단계·부작용으로 3절 복구 분기 |
| 결과 전달 실패 | 기존 로컬 결과·원장·댓글 회수. 설치/계산을 재실행하지 않음 |

Runner 정상이나 GitHub read 성공은 해당 일반챗의 요청 생성 권한 증거가 아니다. 외부 도구 안전 정책은 저장소 지침이나 업무 상시 승인으로 해제할 수 없다. 정확한 거부 사유를 확보하지 못하면 원인 미확정으로 보고하고 허용되는 독립 준비·검토를 계속한다.

기존 유효한 smoke·테스트·Runtime 증거는 재사용한다. 필요한 작업이 없으면 공통 실행기에 최소 모듈과 명세를 등록·검증하고 승인된 갱신 경로를 이용한다. 임의 shell·SQL·다운로드 경로로 허용목록을 우회하지 않는다.

실행 전 현재 작업이 실제로 호출하는 진입점·입력·출력·승인 계약을 확인하고 필요한 의존성만 검증한다. 다른 담당자가 확보한 실PC 경로·source SHA·설정/파일 해시·checkpoint 증거는 원본 결과 링크, 관측 시각, 적용 대상과 현재 계약의 일치 여부를 대조해 재사용한다. 경로 문자열만으로 실행 source를 확정하지 않으며, source나 설정이 바뀌었으면 영향을 받은 항목만 다시 확인한다. 공용 증거와 정정 사항은 #68의 해당 항목에 원본 링크와 유효 범위를 기록해 다른 담당자도 찾을 수 있게 한다.

새 선행 조건을 BLOCKER로 추가하려면 해당 실행 코드나 승인 계약의 필수 조건, 실제 미충족 증거, 차단되는 다음 실행을 명시한다. 독립 게시기가 자체 source·설정·파일 해시 검증으로 실행되는 경우, 호출하지 않는 Core 전체 실행 계보나 전체 폴더 탐색 오류를 자동으로 선행 조건에 넣지 않는다. 반대로 실제 호출·공유 자원·보호 계약에 필요한 검증은 유지한다. 불필요한 조건은 NON_BLOCKING 또는 DEFERRED로 분리하고 작업을 계속한다. 정적 참조 순환 경고만으로 실제 Runtime 순환을 확정하지 않는다.

이전 판단이 잘못됐으면 원래 보고/대기열에 정정과 대체 증거를 연결하고 잘못된 선행 조건을 해제한다. 기존 승인에 포함된 준비·등록은 재승인 없이 수행하며, DB 복원·게시 등 새로운 쓰기 승인이 필요하면 기존 승인과 다른 변경만 구체적으로 제시한다. PR의 main 대비 분기 자체를 설치 불가로 판정하지 않고 실제 충돌·누적 diff·승인 manifest 적합성을 확인한다.

## 3. 연결 장애와 자동 복구

공유 Controller 설치 실패와 RECOVERY_REQUIRED는 [CONTROLLER_RECOVERY.md](CONTROLLER_RECOVERY.md)의 단계별 판정·고정 도구·복구 명세·보관·재개 절차를 따른다. #68의 단일 복구 담당이 다음 행동까지 소유한다. 단순 대기·반복 요청·잠금 임의 삭제로 대체하지 않는다. 무부작용 취소와 부분 적용 rollback, 사후 진단 결과 회수를 구분한다. 공통 상시 승인 범위의 진단·복구 명세 준비는 기능별로 재승인받지 않는다.

Runner Online, 실제 작업 PASS, Controller 자동 업데이트 성공은 별개다. Offline·대기 상태에서 Issue를 반복 생성하지 않는다. Supervisor·watchdog·WScript guardian의 실제 생존과 heartbeat·원장을 확인한다. 오래된 상태 파일이나 PID 존재만으로 정상 판정하지 않는다.

기존 감시·복구 계약을 재사용하고, 유지보수·복구 보류·진행 중 작업과 경쟁해 재시작하지 않는다. 종료가 입증된 제어 전용 lease만 승인된 절차로 보관·인계한다. Core 잠금 삭제, 전체 node.exe 종료, 무조건 재설치는 금지한다.

공유 설치 실패는 다음 순서로 처리한다.

1. #68에서 단일 복구 담당·기존 요청·현재 단계·다음 행동을 기록한다. 현재 lease가 이미 보관됐는지 기존 복구 결과부터 확인한다.
2. 원장·실제 설치 바이트·소유자 생존/identity·stage/backup/backlog·접수 상태를 대조해 설치 전 실패/부분 적용/사후 진단 불명확을 구분한다.
3. 설치 전 무부작용 실패는 정확한 복구 명세와 `maintenance-recovery.mjs inspect`로 적격성을 확인하고 지원되는 `abort-untouched`로 죽은 lease 전체를 보관한다. 단순히 시간이 지났다는 이유로 해제하지 않는다.
4. 부분 적용은 검증된 백업·실제 파일·프로세스·보호 상태로 기존 rollback 경로를 사용한다. 사후 진단·업로드 불명확은 기존 결과를 회수한다. 무부작용 취소 도구를 다른 단계에 사용하지 않는다.
5. 필요한 복구 경로가 미구현이면 실패 단계에 맞는 최소 구현·시험을 보완하고 정확한 실행물을 연결한다. ‘복구하라’는 문장이나 다른 담당자 대기만으로 종료하지 않는다. 구현 전 검사를 제거하거나 임의 수동 복사를 하지 않는다.
6. 원래 실패 원장을 보존하고 복구 결과·실제 SHA·fresh Supervisor·Runner·보호 상태를 확인한다. `ABORTED_UNTOUCHED`, `ROLLED_BACK`, 업데이트 PASS를 구분한다.
7. 원인을 수정하고 현재 설치 SHA로 승인 manifest를 대조한 뒤 새 고유 요청을 한 번 제출한다. 원래 요청·복구 결과 링크를 연결하고 실행·결과 회수 후 후속 담당에게 인계한다.

복구 결과가 불명확하면 원본 lease·보관 위치·복구 예약·완료 기록부터 대조한다. 결과 업로드 실패만으로 복구나 설치를 다시 수행하지 않는다. 이 절차는 모든 기능에 적용하며 공유 설치 차단을 독립 개발·정상 읽기 전용 작업의 전체 차단으로 확대하지 않는다.

현재 시작 방식은 사용자 로그인 기반이다. PC 전원이 꺼져 있거나 로그인 전이면 작업을 받을 수 없다. 이를 코드 장애로 오인하거나 무중단 서비스라고 보장하지 않는다.

## 4. PC 직접 접근이 없는 경우

PC 작업은 특정 제품이나 Codex만 가능한 일이 아니다. 설치된 Runner·독립 유지보수기·승인된 PC 도구를 먼저 사용한다. 이미 설치된 것은 재설치하지 않고 필요한 갱신·인계만 수행한다.

직접 실행 경로가 없고 사용자 실행이 필요하면 기존 설치기·진단기·인계 도구를 호출하는 실제 CMD 또는 ZIP을 제공한다. 명령어 복사·입력, 사용자 파일 작성, 경로·SHA 수정을 요구하지 않는다. 목적·압축 해제 위치·일반 권한·정확히 1회 실행·정상값·STOP 조건을 안내하고 비민감 결과 TXT를 남긴다. 자동 회수가 불가능할 때만 결과 TXT 한 개를 요청한다.

Windows 실검증이 없으면 운영 적용과 검증용 실행을 분리한다. 운영 환경을 변경하지 않는 읽기 전용 진단·임시 폴더 시험용 실행물을 먼저 제공할 수 있다. 이를 운영 적용이 검증된 도구라고 표현하지 않는다. 검증 전용 실행물을 만들기 위해 운영 적용 성공을 먼저 요구하지 않는다.

파일 제공이 불가능하면 정확한 도구 제약을 밝힌다. 실행 파일 없이 준비 완료라고 보고하지 않는다.

## 5. 상시 승인과 안전한 업데이트

### 승인 원칙과 기록

사용자는 이미 승인된 ZGMINI 업무를 수행하기 위해 공통적으로 필요한 아래 준비·등록·설치·검증 절차를 모든 기능과 담당 대화에 상시 승인한다. 특정 기능명에 한정된 승인이 아니며 신규 기능에도 같은 목적과 보호 조건이면 적용한다. 기능이 다르거나 신규 모듈이라는 이유만으로 같은 공통 절차를 다시 승인받지 않는다.

승인 근거는 2026-11-03 사용자의 공통 필수 절차 상시 승인 지시다. 이 절은 아래 공통 절차에 대한 실제 승인 기록이며 단순한 승인 작성 예시가 아니다. 적용 명세에는 업무 목적, 대상 source·경로·파일·데이터, 해당하는 허용 행동, 검증·백업·복구 조건을 기록한다. 명세 작성은 재승인 요청이 아니다. 철회·변경 기록이 있으면 적용한다. 본 업무 자체의 게시·배포 등 별도 효과는 기존 업무 승인 범위를 확인한다.

### 상시 승인 적용 범위

이미 승인된 업무의 실행에 필요한 다음 공통 절차는 기능 구분 없이 재승인 없이 수행한다.

- 제한된 경로의 읽기 전용 진단과 무결성 검사
- 검증된 보관본의 새 격리 경로 복원
- 승인된 기능의 source·입력 경로 등록
- 해당 업무에 필요한 최소 실행 모듈·허용목록·호스트 설정 등록, 자원 제한을 유지한 light/heavy 실행 정책 적용
- 검증된 유지보수 경로를 통한 Controller 설치·갱신 및 필요한 유지보수기 정책 인계
- 승인된 업무를 막는 공용 장애의 읽기 전용 진단, 정확한 복구 명세 작성, 검증된 제어 전용 lease 보관·인계 및 기존 보호 범위 안의 복구·재개
- 동일 목적의 후속 오류 수정과 실행 검증

이 승인은 임의 명령 실행, 포괄적 권한 확대, 관리자·보안 설정 변경, 기존 운영 DB 덮어쓰기·삭제를 포함하지 않는다. 새로운 공급자 호출, D1 게시·사이트 배포는 해당 업무의 기존 승인에 포함됐다면 재사용하고 미승인 효과만 별도로 확인한다. 특정 기능의 계약에 적힌 제한을 다른 기능 전체의 공통 금지로 확대하지 않는다. 실제 변경이 상시 승인 목적·보호 범위를 벗어날 때만 그 차이를 제시한다.

### 기술적 적용

중량 읽기 전용 기능의 새 등록은 기능명별 예외 코드 추가 대신 승인된 공통 자원 프로필을 사용한다. 현재 공통 heavy 프로필은 A/heavy·240초·최소 가용1536MiB이며 purpose=`pc-controller-heavy-readonly`, B scope=`PC_CONTROL_HEAVY_READONLY_UPDATE`로 정확한 파일/명세를 고정한다. 이는 테마/기능 수 제한이 아니라 자원 안전 정책이다. 기본 light 갱신이 heavy를 자동 허용하지 않으며, 기존 한정 계약은 호환 범위로만 유지한다.

승인은 재사용하되 적용 대상의 정확한 SHA·파일 해시·검사 결과·현재 설치 상태·백업·복구 조건은 확인한다. 상시 승인 문서만으로 실행기 권한이 바뀐다고 가정하지 않는다. 필요한 승인 manifest와 실행 정책 반영을 검증된 유지보수 경로로 수행한다. 기존 정책과 허용목록을 우회하지 않는다.

현재 설치 SHA, 승인된 목표 SHA·파일 해시·검사 결과·백업·복구 계약을 확인한다. 최신 main 또는 병합 사실만으로 승인을 대신하지 않는다. 동일 승인 범위는 재승인 없이 진행하고, 새 운영 변경·권한 확대만 별도 확인한다.

공용 Controller·유지보수기 설치는 각 담당자가 따로 경쟁하지 않고 공통 적용 대기열로 조정한다. 적용 담당 한 명이 실제 설치 SHA와 누적 변경을 확인하고, 각 변경의 승인 근거·의존성·실행 순서를 기록한다. 담당이 없으면 준비된 작업의 담당자가 조정안을 등록해 담당을 확정하며, 서로를 기다리는 상태로 방치하지 않는다.

같은 설치 기준에서 함께 적용할 수 있는 승인된 변경은 정확한 통합 manifest로 묶어 한 번 적용한다. 묶음 승인은 개별 변경의 승인 근거를 모으는 것이며 다른 작업까지 자동 승인하는 뜻이 아니다. 통합이 불가능하면 승인된 변경부터 순차 적용하고, 매번 실제 설치 SHA를 읽어 다음 manifest를 갱신한다.

`ALLOWFILE_DIFF_MISMATCH`는 실제 누적 diff와 승인 명세가 다른 것으로 처리한다. 검사를 제거하거나 최신 main 전체를 무조건 허용하지 않는다. 실제 대상의 모든 변경 파일·해시를 각 승인에 대조하고, 미승인 변경은 검증된 선별 경로로 분리하거나 필요한 승인만 확인한다.

Controller 업데이트는 검증된 독립 유지보수기에 `pc-maintenance` 요청으로 수행한다. 일반 `pc-job` Runner가 자신을 교체하도록 하지 않는다. 승인 manifest는 원본 바이트 해시를 사용하고, 요청은 현재 계약으로 검증해 한 번만 생성한다.

기존 작업·업로드 종료 대기 → 요청 보존 → 검산한 백업 → 승인 파일 적용 → Runner 6개 재연결 → 보호 검사 → 사후 진단 → 결과 회수를 확인한다. 기존 사후 진단이 완료됐다면 재사용한다. 유지보수 중 접수된 요청도 계약에 따라 중복 없이 회수한다.

유지보수기 자체의 첫 인계는 별도 절차다. 실행 중인 프로세스의 증거를 소급 생성하지 않는다. 현재 설치 상태에 맞는 정상 종료 또는 종료 입증 후 인계·복구 경로를 사용한다. 검사를 제거하거나 UNKNOWN을 임의로 PASS로 바꾸지 않는다.

유지보수 정책 변경이 필요한 작업은 정책 적용을 선행 의존성으로 등록한다. 예를 들어 heavy 예외가 필요한 작업은 해당 정책의 승인·Windows 검증·인계를 먼저 완료한다. 이 의존성을 무관한 A/light 작업의 전체 중단 사유로 확대하지 않는다.

Windows Startup 환경의 GitHub 인증을 실제로 확인한다. 다른 도구 환경에서 인증이 된다는 사실만으로 대체하지 않는다. 기존 계정을 재사용하고 공식 보안 저장소를 사용하며 토큰을 명령행·파일·로그·Issue에 남기지 않는다.

## 6. 동시 작업과 변경 범위

현재 6개 Runner의 요청 ID·작업폴더·TEMP·캐시·출력·원장을 분리한다. 독립 작업은 병렬 실행하고, 공유 설치·운영 쓰기는 자원별 잠금으로 직렬 처리한다. 무거운 작업은 PC 자원 정책에 따라 대기한다.

동일 운영 파일의 수정·적용 담당은 한 명으로 정한다. 다른 작업자의 미커밋 변경·요청·결과를 보존한다. 서브에이전트·플러그인은 필요한 독립 조사·검토·시험에 활용하되 현재 목표에 불필요한 고도화를 추가하지 않는다.

기능 개발·리뷰·격리 시험은 병렬로 진행하고 공용 운영 적용만 직렬 처리한다. 각 기능 담당자는 PR·정확한 SHA·변경 파일·승인·검사 증거를 대기열에 넘긴다. 적용 담당자는 기존 작업·업로드 종료를 기다려 공용 변경을 수행하고, 설치 후 실제 SHA·모듈별 결과·보호 상태를 원장에 기록한다. 기능 담당자는 이 결과를 재사용해 후속 작업을 이어간다.

대기 보고에는 반드시 대기 항목 ID, 적용 담당, 선행 조건, 다음 실행 조건을 적는다. 다른 담당자의 변경이 있다는 이유만으로 서로 무기한 대기하지 않는다. 적용 담당이 바뀌면 현재 요청·설치 SHA·단계·복구 상태를 명시적으로 인계한다. 대기열은 조정 문서이며 기존 PC lease와 승인 검사를 대체하지 않는다.

이전 선행 장애가 해결됐으면 해당 대기 항목을 정정하고 현재의 실제 다음 조건으로 이동한다. 복구 완료를 못 읽었다는 이유로 같은 잠금 해제를 다시 요구하지 않는다. 설치 담당·해제 조건이 불명확하거나 대기가 순환하면 #68에서 담당과 순서를 정리한다. 공통 예방 코드의 소스 반영과 운영 유지보수기 설치는 별도 항목으로 추적한다.

## 7. 보호와 실패 처리

자동화 보완을 이유로 Core/Korea/Iran, 다른 프로젝트 Runner, 운영 source, 원자료·산식, SQLite·D1, 수집·게시 주기, 예약·배포·DNS를 임의 변경하지 않는다. 별도 업무 승인이 있는 변경만 해당 범위에서 수행한다.

비밀정보를 요청·로그·commit·결과에 넣지 않는다. 유료 서비스·자동결제를 추가하지 않으며 API·저장소·PC 자원까지 무제한이라고 보장하지 않는다.

timeout·부분 반영·통신 오류에서는 실제 설치·프로세스·원장·checkpoint를 먼저 확인한다. 같은 실패를 수정 없이 반복 실행하지 않는다. 결과가 불명확하면 중복 요청을 만들지 않는다. `AUTOMATION_BLOCKED`, 실행 중, 실제 Runtime 실패, 검증된 롤백을 구분하고 영향을 받지 않는 작업은 계속한다.

## 8. 완료·보고·문서 유지

구현·테스트·병합·설치·Runtime 검증을 구분한다. 자동 업데이트 완료는 실제 GitHub 요청으로 승인된 갱신, Runner 재연결, 보호 검사, 사후 진단 및 결과 회수가 확인돼야 한다. BOOTSTRAP_STARTED·코드 병합·Runner Online만으로 전체 완료를 선언하지 않는다.

공통 규칙은 제어 저장소 정본으로 관리한다. 다른 브랜치에는 정본 참조와 해당 작업의 차이·증거만 남긴다. 오래된 지침에는 대체 위치를 표시하되 과거 실행·승인 증거는 보존한다.

특정 기능·진단·과거 설치의 허용/금지 조건에는 적용 대상과 시점을 명시하고 공통 규칙으로 확장하지 않는다. 문서의 승인 범위, 현재 실행기의 기술적 지원 범위, 이미 확인된 과거 실행 증거를 구분한다. 공통 지침과 시작 문서의 요약이 충돌하면 적용 범위를 정정하며 실행기 검사를 우회하지 않는다.

공용 적용 순서와 담당·의존성은 [공용 적용 대기열 #68](https://github.com/ansqhd5774-Choi/zgmini-pc-control/issues/68)에 모으고 `docs/CONTROLLER_APPLY_QUEUE.md`를 따른다. 각 대화에 서로 다른 설치 순서를 따로 유지하지 않는다. 문서 등록을 대기열 자동 실행 기능 구현이나 현재 미적용 모듈 설치 완료로 보고하지 않는다.

최종 보고는 완료 항목, 실제 증거, 중요한 미해결 사항, 필요한 최소 조치만 한국어로 짧게 작성한다.

현재 장애 보고에는 관측 시각·실패 단계·차단 범위·담당·다음 지원 동작을 포함한다. 문서/코드 개선·격리 시험·실PC 조회·실제 복구·설치·GitHub 요청 재개를 구분한다. 상태 snapshot은 영구적인 현재값이 아니며, 증거 없이 자동화 전체 완료나 ‘재발 없음’을 보장하지 않는다.
