## 승인·실행·결과 연결의 반복 정체 방지 — 2026-11-22

- **조회 환경과 기능 상태를 분리한다.** DNS·브라우저 크레딧·커넥터 접근 실패는 그 도구의 관측 한계다. 기존 무료 HTTPS/GitHub/승인 PC 읽기 또는 유효한 수동 Runtime 증거를 사용한다. 같은 JSON 조회를 위해 유료 브라우저를 추가하거나 실패한 수단을 반복하지 않는다. 공개 조회가 불가능해도 독립적인 소스·명세·저장 자료 작업을 전역 중단하지 않는다.
- **승인 정본을 실행 명세에 연결한다.** `PROPOSED_NOT_APPROVED`는 실행 승인이 아니다. 먼저 기존 사용자 승인 원문과 정확한 효과를 대조한다. 이미 승인된 효과의 명세·현재 핀·정상 실행 연결은 담당자가 준비한다. source-only 설치 승인에서 공급자 호출·DB/D1 쓰기를 유추하지 않는다. 실제 부족한 효과만 한 번 구체적으로 결정받고, 동일 질문·승인 후보 문서 수정만 반복하지 않는다.
- **불변의 승인 SHA와 이동하는 main 끝을 구분한다.** 실행할 소스의 정확한 SHA·파일 해시·운영 HEAD/config CAS는 유지한다. 다만 명시적으로 승인된 게시 SHA가 main 계보에 남아 있고 바이트가 일치하면 무관한 후속 main 커밋만으로 승인을 무효화하지 않는다. 승인되지 않은 다른 SHA로 자동 교체하지 않는다. W05처럼 현재 SHA를 명세와 실행 코드 양쪽에 중복 고정해 정규 source 전진마다 코드 수정·CI를 요구하지 않는다.
- **접수 영수증과 완료 영수증은 다르다.** 유지보수 접수 알림은 요청·명세 형식·고유 Claim 확인을 뜻하며 최종 설치 승인 검사나 설치 완료를 뜻하지 않는다. 알림 전송 실패를 새 실행 Gate로 만들지 않는다. 완료 여부는 기존 원장·실제 설치·사후검사·최종 JSON/TXT로 확인한다.
- **최신 원본 요청을 추적한다.** GitHub 댓글이 아직 없으면 기존 requestId의 원장 phase/lastPass/firstFail/updatedAt/postIssueNumber와 보고 상태를 우선한다. 기존 `tools/automation-status.mjs --request-id <원래 ID>`는 실제 접근 가능한 승인 환경에서 사용하는 읽기 경로다. 도구 파일 존재가 일반챗의 PC 접근 권한을 생성하지는 않는다. 원장이 전진하면 RUNNING, 완료 후 업로드 대기는 결과 회수 문제, 관측 불가는 미확인으로 한정한다. 시간 경과나 댓글 부재만으로 FAILED/BLOCKED 또는 새 설치 요청으로 전환하지 않는다.
- **독립 실행을 계속한다.** WPSFD42 수집 승인은 해당 BLS 호출·SQLite append에만 적용한다. QFR 저장 자료의 게시 준비, BEA 정확 원자료 확인, 공개 API 읽기 등은 각각의 승인·의존성 안에서 진행한다. 실측 QFR/BEA API의 `STORED_PROJECTION_PENDING`은 저장형 공개 결과의 미준비를 뜻하며 DNS 장애·원자료 소실을 뜻하지 않는다.
- **실제 완료 증거를 재사용한다.** #2669는 접수 09:32:37→성공 댓글 09:37:12 KST, 실제 설치·사후검사·JSON/TXT가 확인됐다. 이 결과를 댓글 미도착 당시의 가설로 다시 미완료 처리하지 않는다. 092의 설치·자연 실행 인증 완료도 같은 원칙으로 유지한다.

위 기준은 실행 제한을 추가하는 규칙이 아니다. 불필요한 중복 조건을 제거하고, 필요한 승인·출처·동시 변경 보호만 해당 효과에 유지하는 기준이다.

## 2. 일반 작업 실행

### 조회·출력·대화 인계의 범위 관리

GitHub 커넥터와 기존 작업 도구는 유지하면서 현재 목표에 필요한 자료를 단계적으로 조회한다. 이는 증거를 줄이거나 도구를 끄는 규칙이 아니라 불필요한 중복·대량 반환을 줄이는 기본 작업 방식이다. 파일 수·메시지 수·토큰 수를 모든 작업의 고정 상한이나 새 실행 Gate로 만들지 않는다.

- **조회 순서:** 기존 완료 증거와 현재 대상 경로를 먼저 사용한다. 모르면 파일명/함수/오류로 검색하고 관련 함수·변경 부분·실패 구간부터 읽는다. 정의·호출자·설정·테스트·의존성·다른 계열이 판단에 필요할 때만 범위를 넓힌다. 일부만 읽고 저장소 전체·모든 사례를 확인했다고 쓰지 않는다.
- **요청과 원장:** 정상 상태 조회는 자기 원본 Issue/requestId와 정확한 결과를 우선한다. 관련 결과 필드·marker·원문 일부를 먼저 가져오고 승인·중복 방지·인과 분석에 필요한 경우 해당 Issue의 페이지나 관련 사건을 확장한다. 전체 #68·모든 Issue·전체 과거 로그를 기본 입력으로 삼지 않는다. 완전한 페이지 확인이 필요한 검증은 생략하지 않는다.
- **도구 출력:** 검색·필터·필드 선택은 가능한 한 반환 전에 수행한다. 파일 트리·코드·로그·도구 목록·스키마 전체를 무조건 출력하지 않는다. 도구 탐색도 관련 이름/서비스로 좁혀 필요한 설명만 확인한다. 큰 비민감 결과는 기존 승인된 파일/결과 경로에 보존하고 대화에는 필요한 구간·판정·원본 위치를 남긴다. 민감정보·원자료를 외부 공유하기 위한 별도 업로드는 만들지 않는다.
- **잘림과 누락:** 출력 잘림·페이지 누락·요약만으로 전체 검증이 끝났다고 하지 않는다. 필요한 구간을 나눠 읽거나 구조화된 원본에서 해당 필드를 다시 추출한다. 출력 크기 제한을 증거 누락이나 오류 숨김 수단으로 쓰지 않는다.
- **증거 재사용:** 원본 링크·파일/구간·source SHA 또는 관측 시각과 유효 범위를 함께 유지한다. 변경·상충이 없으면 이미 읽은 코드·문서·성공 결과를 재조회·재출력하지 않는다. 요약은 원본의 대체 승인이 아니다. 설치·쓰기 직전의 필요한 현재 preimage·lease·권한·승인·CAS는 계속 검증한다.
- **대화 인계:** 원래 대화 전체 대신 현재 목표·저장소/브랜치·정확 source·승인 범위/제외·마지막 완료 증거·미해결 오류·다음 행동을 전달한다. 실행 중/불명확 요청의 Issue/requestId·Run/attempt·checkpoint·lease/부작용 여부·중복 금지 행동을 빠뜨리지 않는다. 새 대화가 인계를 받았다고 자동으로 실행을 재요청하지 않는다. 실제 원본으로 중요한 판단을 확인하고 기존 실행을 이어간다.
- **한계와 검증:** 커넥터를 매번 끄거나 새 대화로 이동할 의무는 없다. 대화 초과의 원인을 조회량으로 단정하지 않으며 내부 사용량을 확인하지 못했으면 정확한 토큰 잔량·개선율·오류 해소를 주장하지 않는다. 다음 정상 작업에서 불필요한 전체 조회/중복 출력과 증거 누락이 줄었는지 확인한다. 이를 위해 별도 PC 시험·예약·권한·승인 서류를 추가하지 않는다.

### 증거 기반·가설 검증형 문제 해결

장애 해결은 **관측 사실 → 실패 조건 → 원인 가설 → 가설을 구분하는 증거 → 최소 수정 → 실제 결과 검증**으로 진행한다. 이는 작업자의 분석 방식이며 새 승인 Gate·필수 서식·고정 조사 횟수·전담 조직을 추가하는 규정이 아니다. 원인이 이미 충분히 입증됐으면 가설 목록을 억지로 만들거나 조사를 반복하지 않고 수정·실행한다.

1. **현상과 원인을 분리한다.** 사용자가 기대한 결과와 실제 결과, 마지막 성공과 최초 실패를 구체적인 실행·데이터로 확인한다. `BLOCKED`, `STATE_UNKNOWN`, `HTTP 200`, Actions 성공은 상태이지 그 자체로 근본 원인이 아니다. 오류를 만든 코드 조건과 실제 입력을 필요한 범위에서 대조한다.
2. **같이 막힌 문제를 분해한다.** 대상 키·계열·공급자·작업 단계·공유 자원을 나누고 실제 의존성을 확인한다. 같은 시각·같은 오류명만으로 원인이 같다고 하지 않는다. 서로 독립인 문제는 별도로 처리하며 한 대상의 미입증·실패를 전체 선행조건으로 확대하지 않는다.
3. **비교 기준부터 확인한다.** 값이 다르면 두 값의 정의·입력·단위·시간대·as-of·정규화·버전·실행 환경이 같은지 먼저 본다. 해시는 어느 바이트를 대상으로 했는지, 날짜는 관측일/발표일/수집일/가용일 중 무엇인지 구분한다. 비교 기준 차이를 실제 데이터 손상으로 단정하지 않는다.
4. **가설을 구분할 증거를 찾는다.** 현재 사실을 설명할 수 있는 원인과 각 원인이 참/거짓일 때 달라져야 할 관측을 정한다. 기존 코드·원문·실행 기록을 먼저 재사용하고, 판단을 바꿀 수 있는 최소 추가 관측을 선택한다. 진단을 고칠 필요가 있다면 원인을 나눌 독립 검사와 대상 연결 결과를 가능한 한 함께 확보한다. 동일 집계·설치·보고를 반복하면서 원인을 알아내는 방식으로 돌아가지 않는다. 신규 관측이 다른 결과를 낼 근거가 없는 경우 재시도하지 않는다.
5. **증거로 원인을 좁히고 최소 수정한다.** 확정 사실·유력 가설·미확인을 구분한다. source에서 가능한 결함을 재현한 것과 실제 운영 원인을 입증한 것은 다르다. 반대 증거가 나오면 기존 가설과 앞선 설명을 명확히 정정한다. 오류명·안전 검사·증상만 없애지 말고 실패 조건을 만든 데이터 또는 계약·연결·코드를 수정한다. 기존 승인과 실제 운영 보호 범위는 유지한다.
6. **원래 목표로 돌아가 검증한다.** 수정한 범위의 회귀시험 후 실제 실패했던 입력·실행 경로에서 달라진 결과를 확인한다. 코드/CI/설치와 기능·저장·게시 완료를 구분한다. 복원할 수 없는 과거 증거나 실제 권한 제약은 정확히 영향 대상을 남기고 독립 작업을 계속한다. 조사·문서 완료를 기능 완료로 바꾸지 않으며, 같은 진단을 반복하는 대신 다음 허용된 수정·실행으로 이어간다.

분석 근거는 기존 Issue·진행 원장·PR에 필요한 만큼만 기록한다. 사용자가 상세 분석을 요청하지 않았다면 최종 보고는 확인된 원인·변경·실제 검증·남은 영향 범위만 짧게 남긴다. 위 순서를 채우려고 별도 보고서·검사 프로그램·예약을 새로 만들지 않는다.

**재사용 사례:** [W04 실제 검증 #2363](https://github.com/ansqhd5774-Choi/zgmini-pc-control/issues/2363)에서는 BED 27건의 canonical JSON 해시와 HTTP 원문 해시 차이를 재계산으로 입증했다. 누락 History 2,880건은 별개 DOL 계열로 분리했다. 전자는 데이터 변조로, 후자는 BED 해결 대기로 취급하지 않았다. 이 사건의 건수·SHA·제약은 일반 작업에 복사할 고정 기준이 아니다. [원인·수정·실행 근거](https://github.com/ansqhd5774-Choi/zgmini-pc-control/issues/68#issuecomment-7010821813)를 참고하되 같은 검증을 다시 실행하지 않는다.

**기본은 승인된 작업의 진행이다.** 안전 조건은 현재 행동이 실제로 변경하는 대상에만 적용한다. 정상 경로는 **기존 승인·요청 효과 확인 → 대상 자원에 실제 접근 가능한 기존 실행기 선택 → 그 효과에 필요한 확인만 수행 → 작업 실행 → 실제 파일·저장값·공개 결과 확인**이다. 접수·파일 접근·업무 승인·결과 게시 권한은 구분하되 계정명·Runner 라벨만으로 파일 접근을 추정하지 않고 기존 성공 실행과 현재 필요한 대상 연결을 우선한다. 접근 불가능한 Runner로 같은 읽기를 반복하거나, 원본 보안을 약화하거나, 추가 서비스 계정·Controller·재승인 단계를 기본 경로로 만들지 않는다. 조회·코드 준비·격리 시험을 위해 운영 설치·게시 승인이나 전체 시스템 정상 증명을 먼저 요구하지 않는다. 제목·표시 문구·다른 사건의 과거 실패는 그 자체로 중단 사유가 아니다.
새 조건을 추가하거나 기존 조건을 확대하기보다, 현재 차단이 데이터 손상·권한 초과·중복 효과·실제 충돌 중 무엇을 막는지 확인하고 해당 단계에 한정한다. 관련 없는 관측 실패는 미확인으로 남기고 가능한 승인 작업을 계속한다. 검사가 실패한 채 우회 실행하지 않고 불필요한 검사 결합을 수정한다.
검증·승인·실행 증거는 같은 범위에서 재사용한다. 이미 승인된 업무의 manifest·해시·최소 변경안은 담당자가 작성하고 진행한다. 자료 미작성·인계 댓글 미수신·독립 기능 미완료를 이유로 사용자에게 같은 승인을 다시 요구하지 않는다. 실제 범위 밖 운영 변경이나 해결되지 않은 직접 위험이 있을 때만 그 행동을 보류한다.

### Cloudflare 운영 읽기 — 공식 PC·Wrangler OAuth 경로 (2026-11-24)

Cloudflare 활성 Production Deployment·Version·traffic·`zgmini.kr` 바인딩 확인의 **공식 1차 실행 경로**는 이미 등록·설치되어 실제 Windows PASS를 획득한 A/light·90초 `w05-cloudflare-deployment-readonly`다. 운영 PC 내부의 기존 Wrangler OAuth와 고정 Cloudflare REST API GET을 재사용하고, `pc-job` Issue → Actions/Runner → JSON/TXT 원격 readback으로 검증한다. **웹 디버그, 유료 브라우저, 사용자 Cloudflare 대시보드 수동 조작을 선행조건으로 만들지 않는다.** [실제 구현·요청·보안·증거·실패 기준](CLOUDFLARE_OFFICIAL_PC_READONLY_STANDARD.md).

유효한 [실PC A #3306](https://github.com/ansqhd5774-Choi/zgmini-pc-control/issues/3306)·[원본 JSON](../results/45373166159-1-seat-4.json) 증거는 해당 관측 시각/Version 범위에서 재사용한다. 재조회가 필요할 때만 고유 요청으로 단회 실행한다. 새 Worker/계정이나 Cloudflare **쓰기**(배포, route/traffic, DNS, D1, 설정)를 A 조회의 권한으로 확대하지 않는다. `sourceShaVerified=false`는 Cloudflare API의 독립 Git SHA 증명 미확정으로 유지하며, GitHub 공식 빌드 Version 일치 및 활성 배포 읽기 PASS와 구분한다. 기존 Controller 미설치가 실제 확인된 경우에만 정규 승인 B 등록 절차를 사용하고, 매 조회마다 재설치하지 않는다.

### 업무 데이터 보호와 실행에 필요한 조정 상태

읽기 전용은 업무 행·산식·DB schema·공개 값에 쓰기를 허용하지 않는 계약이다. 정상적인 조회에 필요한 SQLite 읽기 잠금과 WAL 공유 메모리의 생성·갱신·정리를 업무 데이터 쓰기와 동일하게 금지하지 않는다. SQLite 내부 조정은 승인된 고정 조회에서 SQLite 엔진이 수행하며, 작업자가 보조 파일을 직접 생성·삭제하거나 journal mode·checkpoint를 강제로 바꾸지 않는다.
공통 SQLite 읽기는 native readOnly와 query_only를 함께 사용하고 하나의 읽기 트랜잭션에서 일관된 커밋 snapshot을 조회한다. 활성 Core 중단·원본 파일 전체 바이트 동결·모든 WAL 파일의 사전 존재를 조회 선행조건으로 요구하지 않는다. 보조 파일 조합만으로 정상/손상을 단정하지 않고 SQLite가 형식·복구·잠금을 처리하게 한다. 실제 잠금 대기는 해당 조회 범위의 bounded busy로 다루며 다른 업무의 전역 BLOCKED로 확대하지 않는다.
읽기 연결에 immutable=1 또는 nolock을 붙여 운영 DB의 변경 감지·잠금을 우회하지 않는다. 불변으로 확보된 별도 입력은 그 입력 계약을 따른다. 결과의 운영 쓰기 0은 해당 작업이 수행한 업무 데이터 변경이 0이라는 뜻이며, 다른 Core의 정상 갱신이나 SQLite 조정 파일의 불변을 주장하지 않는다. 실제 데이터 쓰기·설치·게시의 승인/CAS/백업 계약은 유지한다.

순수 조회 예외는 설치된 실행기가 명시적으로 지원하는 고정 operation에만 적용한다. Issue에 임의 effect나 shell·SQL·경로·명령을 넣어 권한을 확대하지 않는다.
조회가 성공해도 보호 확인이 실패하면 읽기 결과와 보호 미확인을 따로 보고한다. READONLY_RESULT_PROTECTION_UNVERIFIED는 시스템 정상이나 쓰기 승인 PASS가 아니다. 실제 보호 drift·예기치 않은 작업 재등록·무결성 오류는 계속 차단한다.
현재 설치된 허용목록/schema에 맞는 Issue를 고유 chatId/requestId로 한 번 접수하고 status/code/lastPass/firstFail·실제 실행 SHA·TXT/JSON·원본 댓글을 회수한다. 요청 UUID/접두사는 실제 계약으로 검증한다.
대화 추적용 chatId를 권한 증명이나 모든 경로의 UUID 전용 Gate로 사용하지 않는다. 정규 유지보수는 기존 UUID 및 `chat-` 뒤 영소문자·숫자·하이픈 1~75자의 대화 라벨을 수용한다. 요청 단회성과 승인 범위는 requestId 원장·작성자 인증·정확한 manifest/source로 검증한다.
원격 source, 실제 Controller source, PC 운영 HEAD/config.source, 검사 대상 source를 구분한다. 파일 존재·해시 확인에 현재 실행 중 Core의 전체 계보를 새 필수조건으로 붙이지 않는다.
동일 source·환경·효과의 유효한 실PC 증거는 재사용한다. 미지원 작업은 기존 공통 실행기에 최소 명세/모듈을 등록·검증한다. 임의 원격 스크립트로 우회하지 않는다.

### 공통 프로세스 총괄 — 요청 가능 업무·접수·작업 회신 (2026-11-17)

총괄 지원 범위는 공통 실행·Runner, Controller 진단/설치·복구, Writer 수신/manifest, 공유 자원, 공통 결과 회수, 승인 계약, 인계 경로다. 기능별 산식·ETF 선정·데이터 공개 결정은 원담당에게 유지한다.
기존 agent-handoff Issue의 ZGMINI_AGENT_HANDOFF_V1과 원본 요청·실패·source·checkpoint를 사용한다. 중앙 #68 직접 인계도 별도 접수 원천이며 고유 업무로 중복 제거한다.
접수 → 후보 → 실제 인수 → 작업 → 결과 반환 → 원담당 재개를 구분한다. 후보 선정은 인수/실행이 아니다. 이미 선정된 미인수 건도 OWNER_ACTION_REQUIRED로 유지한다.
현재 담당자가 인수했으면 기존 ACKNOWLEDGED → WORKING 영수증을 확인하고 승인 행동을 수행한다. 자동 연결 확인이 안 된다는 이유로 이미 인수한 작업을 사용자 재전달 대기로 돌리지 않는다.
중개기 고정 NOT_CONFIGURED는 별도 중앙 AI 처리자의 실제 활성 상태를 조회한 값이 아니다. 자동 AI·다른 대화 자동 재개는 실제 증거 없으면 미검증으로 보고한다.
소스 수정 결과는 기존 PR/CI 결과 계약으로 반환한다. **코드 수정 없는 고정 읽기 진단**은 ZGMINI_AGENT_HANDOFF_DIAGNOSIS_V1로 검증된 PC Issue/Run·JSON/TXT를 반환한다. 진단을 반환하려고 무의미한 PR을 만들지 않는다.
진단 영수증은 해당 조회의 증거이며 사건 근본 해결·운영 쓰기·원담당 채팅 수신을 승인하지 않는다. 상세 [중앙 인계 계약](AGENT_HANDOFF_CENTRAL_ORCHESTRATOR_V1.md).
진단 요청의 식별은 인증된 작성자·pc-job 라벨·요청 schema·실제 실행 증거로 한다. 자동 postcheck처럼 제목이 달라도 같은 계약이면 인정한다. 서로 다른 검증된 진단 결과는 이력을 보존해 회신하며, 같은 resultId의 내용 충돌과 같은 결과의 중복 전송만 차단한다.

### 자동 장애 감지·인계·능동 진단의 사용 범위

기존 자동화는 사건 감지·증거 수집·분류·후보 선정·결과 전달을 돕는다. 다음 단계를 서로 구분한다.

| 경로 | 수행하는 일 | 그 결과만으로 주장할 수 없는 것 |
|---|---|---|
| 일반 PC 작업 | 설치된 operation을 실행하고 고유 Issue/Run의 결과를 회수 | 다른 기능 전체 완료 |
| PC/Writer B 실패 접수 | 실제 원본 실패 증거를 검사해 agent-handoff 사건을 중복 없이 접수 | PC 복구·코드 수정·운영 재실행 |
| 인계 라우팅·후보 선정·관제 | 기존 사건의 분류·담당 후보·처리 상태를 정리 | 실제 담당 대화의 수신·인수·착수 |
| R1 능동 진단 | 최근 Actions 실패·시간 초과의 관련 실행·단계·제한된 로그 신호 비교 | 공급자/운영 PC의 근본 원인 확정 |
| R2 증거 심화 | 원본 사건·고정 소스·같은 SHA 실행 이력의 정적 비교와 정책 결정표 검토 | 소스 의미 분석·실제 코드 실행 시뮬레이션·수정 성공 |
| R3 범위 탐색 | 취소·조치 필요·장기 대기·미갱신 사건/PR·workflow 상태 등 GitHub 메타데이터 관측 | 취소=장애, 대기=PC 고장, 전체 운영 상태 확인 |
| 실제 담당 처리·원본 결과 반환 | 승인된 조사·수정·검증을 수행하고 원본 요청에 결과 연결 | PC 미적용 상태의 운영 완료·다른 대화 자동 재개 |

자동 접수는 `.github/workflows/agent-handoff-pc-failure-intake.yml`, `agent-handoff-writer-b-failure-intake.yml`, `agent-handoff.yml` 등 기존 계약을 사용한다. 활성화 변수는 각각 `ZGMINI_PC_HANDOFF_INTAKE_ENABLED`, `ZGMINI_PC_HANDOFF_WRITER_B_INTAKE_ENABLED`, `ZGMINI_AGENT_HANDOFF_ENABLED`다. **소스 존재·변수 true·workflow active·실제 실행·사건 접수·담당 처리·운영 해결은 서로 다른 증거**다. 필요한 문제가 있을 때만 현재 변수·트리거·권한·Run·영수증을 구분해 확인하고 매 업무마다 전부 재검사하지 않는다.

능동 진단과 범위 탐색은 지원되는 저장소·조회 범위의 보조 증거다. 코드를 읽거나 실행하지 않은 결정표 결과를 근본 분석·자동 수리로 과장하지 않는다. 기존 GitHub 예약·보조 이벤트와 ChatGPT/Codex 예약은 별개이며, GitHub cron은 정시·무중단 실행을 보장하지 않는다. 이 지침을 적용하기 위해 새 예약·별도 Runner·AI 서비스·Workflow를 만들지 않는다.

자동 장애 사건과 #68의 직접 공유 지원 요청을 모두 기존 실접수로 취급하고 원본 사건별로 중복 제거한다. 대기 라벨 수만으로 전체 업무의 대기 건수를 계산하지 않는다. 일반 업무는 자기 원본 Issue·requestId·결과를 추적하고 #68/진단 원장의 전체 이력을 매번 전수 조회하지 않는다.

이미 인수한 담당자는 원래 목표의 다음 승인 행동을 직접 수행한다. 봇의 NOT_CONFIGURED/AWAITING 표기만으로 다른 처리자의 실제 상태를 단정하거나 자기 작업을 사용자 재전달 대기로 돌리지 않는다. 반대로 실제 전달 경로·실행 증거 없이 AI 자동 처리·타 대화 수신·재개를 주장하지 않는다.

관측은 관측한 범위만 보고한다. 불완전 페이지·일부 사건의 접근 오류·원장 포화·무관한 과거 취소를 전체 정상 또는 전체 장애로 바꾸지 않는다. 구현이 지원하는 사건별 오류 격리·조건부 조회·원장 분할을 재사용하고 다른 사건을 막는 실제 결합은 그 코드 범위에서 수정한다. 확인되지 않은 항목은 미확인으로 보존한다.

수정한 소스는 기존 PR/CI 결과 계약, 코드 수정 없는 승인 진단은 기존 진단 결과 계약으로 회신한다. 진단을 반환하려고 PR을 억지로 만들지 않는다. 자동화 영수증의 상태를 실제 성공으로 바꾸거나 원본 실패를 삭제하지 않는다. 상세 계약은 [중앙 인계](AGENT_HANDOFF_CENTRAL_ORCHESTRATOR_V1.md), [능동 진단 R1](HANDOFF_PROACTIVE_GITHUB_DIAGNOSTICS_R1.md), [증거 심화 R2](HANDOFF_DEEP_GITHUB_EVIDENCE_R2.md), [범위 탐색 R3](HANDOFF_WIDE_GITHUB_SCOUT_R3.md)를 현재 구현과 함께 필요한 범위에서 확인한다.

## 3. 연결 장애와 자동 복구

Runner Online, Job 배정, 단계 시작, Controller 실행, 실제 기능 PASS, 결과 반환은 별개다. queued/timeout/도구 접근 실패만으로 PC 기능 실패를 확정하지 않는다.

| 관측 | 확인·대응 |
|---|---|
| 도구 미연결·권한 부족 | 연결 권한의 해당 범위를 구분한다. PC 장애·설치 손상으로 확대하지 않는다. |
| 요청 형식 오류 | 현재 schema에 맞춰 준비한다. 접수 불명확이면 먼저 기존 ID를 확인한다. |
| 도구 안전 검사 거부 | 거부된 정확한 행동·비민감 사유를 확인하고 그 거부를 다른 도구·명령으로 우회하지 않는다. 허용된 준비·독립 작업은 계속한다. |
| 접수 호출 timeout·응답 유실 | Issue/requestId·원격 반영 상태를 먼저 대조하고 중복 생성하지 않는다. |
| queued·미접수 | 실제 대상 host/label·Online/Busy·Job/Worker 시작·receiver·lease를 영향 범위에서 확인한다. |
| HTTP 403 | 어느 API와 어느 권한인지 구분한다. Runner 목록 API의 403 하나로 로컬 Controller 전체를 불량으로 판정하지 않는다. |
| 실제 실행 실패·부분 적용 | 최초 실패 조건·부작용·설치 파일·원장·checkpoint에 맞춰 해당 작업의 복구로 분기한다. |
| 결과 업로드·댓글 전달 실패 | 기존 결과를 회수한다. 이미 입증된 실행 결과를 지우거나 계산·설치를 다시 실행하지 않는다. |

신뢰된 요청이 실행 전 형식 검사에서 거부되면 지원되는 접수기는 원본 Issue에 `REQUEST_REJECTED_BEFORE_EXECUTION`과 정확한 code·실행 시작 여부를 반환한다. 접수 실패를 PC Runtime 실패로 표현하지 않는다. 응답이 없다는 사실만으로 미접수라고 단정하지 않는다.
기존 요청의 Run/attempt·실제 Runner·원장·checkpoint부터 확인한다. 종료된 read-only 요청의 내부 로그가 없다는 이유로 현재 유효한 승인 읽기를 전역 금지하지 않는다. 새 조회는 같은 ID 재실행이 아니며 현재 scope·정상 경로를 확인한 고유 요청 한 번으로 한다.
쓰기·공급자 호출·부분 적용·활성 lease·자식 종료 불명확에는 이 읽기 재개 기준을 확대하지 않는다. 실제 설치·원장·저장값을 먼저 대조한다.
Offline이면 Issue를 반복하지 않고 기존 Supervisor/watchdog/guardian·heartbeat·실제 생존과 원장을 확인한다. PID나 오래된 파일만으로 정상 판정하지 않는다.
사용자 로그인 기반 시작의 한계를 유지한다. PC 전원 꺼짐·로그인 전은 코드 장애가 아니다. 기존 복구 계약 [RUNNER_RECOVERY](RUNNER_RECOVERY.md), [CONTROLLER_RECOVERY](CONTROLLER_RECOVERY.md)를 적용하며 Core lock 삭제·전체 node 종료·무조건 재설치는 하지 않는다.

## 4. PC 직접 접근이 없는 경우

기존 Runner·독립 유지보수기·승인된 PC 도구를 우선한다. 설치된 환경을 다시 설치하지 않는다. 도구 미연결을 PC 장애로 판단하지 않는다.
사용자 실행이 꼭 필요하면 기존 검증 도구를 호출하는 실제 CMD/ZIP을 제공한다. 명령 복사·파일 작성·경로/SHA 편집을 사용자에게 요구하지 않는다.
목적·준비 상태·실행 위치·일반 권한·정확히 한 번·정상값·STOP·금지 행동·보낼 결과를 안내한다. 비민감 TXT와 자동 회수를 우선한다. Windows 미검증 도구를 검증된 운영 도구로 표현하지 않는다. 파일 제공이 불가능하면 정확한 도구 한계를 밝힌다.

## 5. 상시 승인과 안전한 업데이트

### 2026-11-23 공통 변경의 장애 격리

공통 Controller의 변경 실패를 기존 실행 기능의 장애로 자동 확대하지 않는다. 현재 파일·Supervisor·보호 기준과 intake가 정상임을 입증하면 실패한 후보만 중단한다. 새 기능은 기존 승인 소스 번들·등록 계약과 실행기를 우선 재사용하며, 기능 변경을 이유로 무관한 공통 파일을 함께 교체하지 않는다.

설치 준비(stage)는 intake 중지보다 먼저 수행한다. stage 실패를 격리할 수 있는 경우는 **실행 전 해당 요청의 후보 namespace가 없었음**, 후보 파일이 정확한 요청별 경계 안에만 있음, 기존 Controller 전체 바이트·owner·보호 기준이 유지됨, 현재 intake active와 설치 SHA가 독립 재조회로 일치함을 모두 입증한 경우다. 이때 기존 `BLOCKED`와 `STAGING_ONLY_ISOLATED_VERIFIED`를 사용하고 후보 파일을 보존하며 공용 설치 lane을 복구 필요 상태로 남기지 않는다. 증명 누락·경로 alias·예상 밖 파일·원본 변경·intake 불명은 기존 RECOVERY_REQUIRED 보호를 유지한다. 부분 staging을 일반적인 무변경 실패로 취급하거나 자동 삭제하지 않는다.

실제 stop/switch 전 실패와 전환 후 실패를 구분한다. 준비 실패에는 Supervisor 종료·정상 파일 복원·Backlog 재실행을 추가하지 않는다. 전환 후 확정 실패에는 기존 검증된 rollback을 적용하며, 상태 불명에는 원본 원장·실제 효과를 대조한다. 운영 상태 기록은 실제 완료 효과와 일치해야 한다.

복구는 고장 난 Controller/pc-job을 실행 경로로 요구하지 않는 기존 독립 Windows 도구를 사용한다. 환경변수에 Runner 표시가 없다는 사실만으로 독립성을 주장하지 않으며 실제 프로세스 계보·설치 소스·승인 CAS를 검증한다. 운영자 인증 불명·시간 초과·검증 도구 부재는 각각 비민감 오류 코드로 보고하고 검증을 우회하지 않는다. 별도 수신기/관리자 권한/새 예약을 기본 해결책으로 추가하지 않는다.

수정 소스 병합, 유지보수기 실제 handoff, 기존 요청 복구, 업무 실행은 서로 다른 완료 상태다. 같은 자원의 활성 복구 lease가 있으면 이를 보존하고, 독립적으로 가능한 소스/격리 시험은 계속한다. 근거 없는 전체 완료를 선언하지 않는다.

공통 유지보수 source CI는 Workflow와 검사 대상 소스를 동일한 PR 통합 tree(`github.sha`)에서 실행하고 실제 검사 SHA를 기록한다. 최신 base의 검사 목록을 이전 PR head에 섞어 없는 검사 파일로 실패시키지 않는다. 이는 통합 검증이며 별도의 승인 target SHA·파일 해시 검증을 대신하지 않는다. source CI 오류를 운영 기능 실패로 확대하거나 검사를 삭제해 통과시키지 않는다.

**2026-11-21 정상본 복귀 우선:** 모든 승인된 변경 작업은 기존 manifest/journal에 해당 범위의 이전 정상 상태·복귀 방법·복귀 확인을 포함한다. 확정 실패 시 운영 복구를 원인 분석보다 우선하고, 검증된 정상본 복귀 후 기존 승인 업무를 계속한다. Controller/Writer뿐 아니라 배포·DB·게시에도 효과별 복원/보상 범위를 적용하되 읽기 전용에는 불필요한 롤백을 요구하지 않는다. 결과 불명·동시 변경은 실제 상태/CAS를 확인하며 임의 덮어쓰기·재실행을 하지 않는다. 새 승인·전역 Gate·예약 감시를 추가하는 지침이 아니다. [공통 실행 기준](ROLLBACK_FIRST_WORKFLOW.md).


사용자가 승인한 업무의 필수 공통 등록·격리 복원·최소 실행 정책·Controller/Writer 설치·유지보수기 인계는 정확한 효과 범위에서 재승인 없이 수행한다. 게시·배포·관리자/보안 변경은 그 업무 승인 범위를 따른다. 코드 병합이나 도구 접근 권한이 업무 승인을 대신하지 않는다.
현재 설치 → 정확 목표·파일별 해시·raw manifest 해시·검사·백업/복구 조건을 확정한다. 누적 diff와 allowFiles가 다르면 승인되지 않은 변경을 끼워 넣지 말고 정규 최소 목표 commit/manifest 또는 승인된 순차 적용을 준비한다.
설치된 실행기가 지원하는 정규 선별 적용(selectiveSource)도 재사용할 수 있다. 승인된 main 출처·고정 대상 branch/commit·실제 설치본과의 정확 diff·파일 해시·선택 적용 pin을 현재 계약으로 검증한다. 과거 ‘모든 목표는 main 조상이어야 한다’는 조건을 다른 계약에 그대로 전파하지 않으며, 미지원 설치기에 문서만으로 이 기능이 생겼다고 가정하지 않는다. 미승인 main 변경은 함께 설치하지 않는다.
요청 작성에 지원되는 `prepareControllerUpdateRequest(rawManifestBytes, {installedSha, chatId})` 등 기존 생성기·검증기를 사용해 수작업 ID/바이트 해시 오류를 줄인다. Controller 요청은 이를 재사용하는 `tools/maintenance-request.mjs`로 제목·라벨·본문을 함께 만들고 단회 제출·원격 readback을 수행한다. 제출 전 사용자 TEMP의 고유 영수증을 저장하며 timeout/전달 불명은 같은 영수증 `reconcile`로 조회하고 새 POST를 하지 않는다. [제출 공통 경로](CONTROLLER_AUTO_UPDATE.md)를 따른다. 명세 작성·요청 저장은 새 업무 승인이나 실제 PC 접수·설치 성공이 아니다.
Controller는 독립 pc-maintenance로 갱신한다. 일반 pc-job이 실행 중인 자기 Controller를 교체하지 않는다.
기존 작업/업로드 종료 → 요청 보존 → 검산한 백업 → 승인 파일 적용 → 전용 Runner 재연결 → 보호 검사 → 기능별 사후 검사 → 결과 회수 순서로 진행한다. 접수/backlog도 중복 없이 회수한다.
유지보수기 자체 첫 인계는 별도 계약을 따른다. 출처 증거를 소급 생성하거나 UNKNOWN을 PASS로 바꾸지 않는다. Startup 환경의 실제 GitHub 인증을 확인하며 비밀값은 공식 저장소 밖으로 내보내지 않는다.

## 8. 완료·보고·문서 유지

관제의 PENDING_OWNER_ACK는 **정형 인수 영수증 미확인**이지 실제 미처리 확정이 아니다. 기존 Owner 계정의 처리 댓글과 원본 요청·후속 결과를 먼저 확인하며, 이 표시만으로 새 영수증·재접수·PC 재실행을 요구하지 않는다. 일반 댓글과 원본 링크는 검토 근거 위치로 연결하되 자유 형식 문구만으로 인증된 인수·운영 성공·사건 종결을 자동 판정하지 않는다. 일반챗 자동 호출은 현행 관제의 지원 기능이 아니며 NOT_CONFIGURED를 해결 대기나 실행 선행조건으로 만들지 않는다.


봇 결과는 기존 기계 판독 영수증과 JSON/TXT 계약을 보존하면서, 사람이 읽는 부분에 **이번에 완료한 범위·최초 차단 조건·다음 행동·기존 결과 링크**를 먼저 표시한다. 설치 검증은 계산/게시 완료가 아니고, 진단 반환·후보 선정은 실제 담당 인수나 장애 해결이 아니다. 원격 결과 회수 미확인을 로컬 설치 실패/복구 완료로 바꾸지 않는다.

이미 안전하게 정제한 실패 세부값만 사용한다. 원장에 없는 실패 파일·기대/실측 SHA·원인을 추정하거나 비밀/원문 오류를 새로 출력하지 않는다. 필요한 세부값이 없으면 그 한계를 밝히고 기존 결과에서 해당 범위만 확인한다. 이 보고 개선은 새 승인·진단·운영 재실행 조건이 아니다. 관제의 다음 행동은 참고 안내이며 ACK/WORKING/실제 실행을 자동 생성하거나 다른 대화의 인수를 가장하지 않는다.


현재 목표를 실제 막는 조건만 BLOCKER다. 도구 제약(AUTOMATION_BLOCKED), 실제 기능 실패(RUNTIME_FAILED), 자원 대기, 실행 중, STATE_UNKNOWN, 검증된 복원을 구분하고 영향 없는 작업은 계속한다.
구현·테스트·병합·설치·실제 기능 실행·게시·API/UI·다음 자연 실행을 따로 보고한다. HTTP200·CI·Runner Online·BOOTSTRAP_STARTED로 종단 성공을 선언하지 않는다.
기존 실PC/Provider/DB/배포/사용자 수동 검증은 유효 범위에서 재사용한다. 자동화 접근 실패로 완료된 Runtime 증거를 취소하지 않는다.
완료는 실제 수행·고유 요청/Run·결과쌍·보호/사후 readback으로 판정한다. 열린 Issue·대기 라벨·과거 실패 하나를 현재 전역 장애로 재사용하지 않는다. 성공 후 상태를 정리하되 과거 실패/승인 증거는 보존한다.
보고는 한국어로 이번 결과·실제 증거·중요한 미해결 범위·다음 필수 행동만 짧게 작성한다. 동일 상태·유효한 과거 성공을 신규 성과로 반복하지 않는다. 근거 없는 완료율이나 재발 없음 보장을 쓰지 않는다.
[성공 실행물 색인](SUCCESS_EVIDENCE_REUSE.md)의 공통 실행 구조를 재사용한다. 새 gate·예약·문서를 매 작업의 완료조건으로 만들지 않는다.
이 정본과 GENERAL_CHAT_PREWORK.md를 함께 유지한다. 프로젝트 상시 지침은 공통 사고방식과 범위를 연결하고, 작업 전 전달문은 이 정본의 요약으로 사용한다. 장문의 과거 전달문 사본을 별도 현행 정본으로 운영하지 않는다. GitHub 반영은 다른 일반챗의 자동 학습이나 PC 설치가 아니다. 이전 정본은 [역사 보관본](history/PC_AUTOMATION_STANDARD_BEFORE_EFFECTS_20261119.md)이며 현재 차단 조건으로 적용하지 않는다.


### 원자료 해시·History 복구 검증의 범위와 종료 (2026-11-19)

원자료 HTTP 문자열의 SHA와 정렬·정규화한 JSON의 SHA는 다른 계약이다. 기존 수집기가 어느 바이트를 해시했는지 먼저 실제 코드와 대조한다. 저장된 원문·원래 해시·수집 영수증은 덮어쓰지 않는다. 구형 형식 호환은 원문 SHA·snapshot ID·해당 버전의 정규화 알고리즘 재계산·수집 run 연결을 각각 검증해 별도 증거로 남긴다. 형식 호환의 입증은 원래 필드의 엄격 검증을 소급 PASS 처리하거나 당시 가용 시각/PIT 인증·History 쓰기를 허가하지 않는다.

복구 대상 키에 직접 연결되는 원자료와 시각만 판단한다. 다른 공급자·다른 계열의 불일치 또는 다른 키의 충돌을 전체 복구의 필수 대기로 확대하지 않는다. 원문과 run이 인증된 자료는 누락 History 키별로 연결·분류하며, 손상·미연결·과거 가용일 입증 불가능은 해당 키에만 사유를 남긴다. 현재 수집 시각을 과거 최초확인 시각으로 바꾸지 않는다.

원인 조사는 본문·메타데이터·수집 run·대상 키 연결을 동일 읽기 트랜잭션에서 함께 확인해 오류 이름 하나마다 코드 수정·설치·재조회하는 반복을 줄인다. 이미 확보한 자료로 판정 가능한 키는 독립 진행한다. 증거가 남아 있지 않은 키는 미입증으로 종결해 보고하며 반복 조회로 복원된다고 주장하지 않는다. 43번 같은 검증 단계의 분류 완료와 실제 복구 가능·운영 저장 완료를 구분한다.
