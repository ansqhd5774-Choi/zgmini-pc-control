# ZGMINI 자동화 프로세스 전문가 작업 기준

**2026-11-23 변경 실패 격리:** [공통 정본](PC_AUTOMATION_STANDARD.md)의 공통 변경 장애 격리를 따른다. 후보 준비는 정상 실행·intake를 유지한 상태에서 수행하고, 입증된 후보 namespace 실패만 해당 요청에 한정한다. 기존 실행이 입증되지 않으면 안전 중단을 유지한다. 기능 추가는 기존 승인 모듈·등록 경로를 우선 재사용하며 고장 난 Controller에 복구 실행을 다시 의존시키지 않는다. 소스 병합과 운영 handoff·복구·기능 완료를 구분한다. 검증되지 않은 롤백·새 전역 Gate·무관한 기능 변경을 만들지 않는다.

## 2026-11-23 사용자 최종 결정 — GitHub Actions 15분 예약 장애 조사 종료

**기술 상태와 작업 상태를 분리한다.** 기존 GitHub Actions `schedule`의 15분 간격 안정화는 사용자 판단에 따라 개선 시도를 **종료**했다. 예약 이벤트의 실제 누락과 불규칙한 실행은 **미해결 사실로 보존**하며, 해결·정상화됐다고 보고하지 않는다. 기존 등록 Cron과 정상 실행 중인 Workflow·Runner, 운영 원본·결과 이력은 유지한다.

**재개하지 않을 업무(명시적인 새 사용자 지시가 없는 한):**
- 동일 예약 누락 원인에 대한 외부 사례 재검색·교차 검증·반복 실험·추가 Cron 조정
- GitHub Support 이메일·티켓 문의 재추진 및 이를 다음 작업으로 제안하는 행위
- 외부 스케줄러·대체 예약·추가 Runner/Workflow/폴링 또는 유료 서비스 도입을 해결책으로 추진하는 행위
- 이미 종료한 관련 개발 Issue·PR을 다시 열거나, 미해결 예약 장애를 이유로 새 중복 개발 Issue·PR을 생성하는 행위

**운영 원장과 개발 작업을 구분한다.** [#1743](https://github.com/ansqhd5774-Choi/zgmini-pc-control/issues/1743)·[#2427](https://github.com/ansqhd5774-Choi/zgmini-pc-control/issues/2427)은 과거 및 자연 실행 증거를 보존하는 **OPEN 원장**이다. OPEN 또는 예약 누락 수치가 새 진단·지원 문의·개발 재개의 승인이 아니다. 기존 증거를 필요한 현행 업무 검증에 재사용하는 것은 허용하되, 중단한 예약 개선 연구를 다시 과제로 만들지 않는다.

**계속할 승인 업무:** GitHub 이벤트 기반 접수·후보 선정·관제, Runner 대기·중복 실행 제거와 이미 구현한 변경의 실제 Runtime 검증 등 **독립적으로 승인된 공통 자동화 개선**은 계속한다. 예약 장애를 이 업무들의 전역 BLOCKER로 만들지 않는다. 사용자가 예약 장애에 관해 **새롭게 명시한 지시**가 있을 때에만 해당 범위를 새로 판단한다. 이 결정은 보안·무결성 검사 완화, Cron 삭제, Workflow 비활성화 또는 재승인을 뜻하지 않는다.

**재발 방지:** 신규 대화·예약 실행은 관련 다음 작업 선정 전에 이 종료 결정을 계승한다. 상태 보고에는 `15분 예약 불규칙 — 기술 미해결 / 조사 종료(사용자 결정)`로 표시한다. 동일 원본 Run/외부 사례 조회·동일 Support 경로 반복을 성과로 집계하지 않는다.

## 1. 목적

자동화의 목적은 **승인된 작업을 더 빠르고 안정적으로 완료하는 것**이다.

진단·승인·검증 단계를 늘리는 것 자체를 개선으로 평가하지 않는다. 작업이 막혔다면 실제 실패 조건을 찾아 필요한 최소 변경으로 해결하고, 요청 범위의 실제 결과까지 확인한다.

이 문서는 기존 공통 지침을 보완한다. 새로운 승인 Gate나 운영 권한을 생성하지 않는다. 사용자의 최신 지시와 현재 승인 범위를 우선한다.

## 2. 담당 범위

다음 공통 실행 과정의 결함을 개선한다.

- GitHub 요청 접수와 작업 분류
- Runner 배정 및 실행 계정 연결
- Controller·공통 Writer 실행과 유지보수
- 상태 판정, 오류 전달, 결과 회수
- 작업 소유권과 담당자 인계
- 실패 후 복귀 및 중단 작업 재개
- 반복 검사·중복 요청·불필요한 대기 제거

기능별 산식·ETF·원자료 정책·UI를 공통 자동화 개선의 명목으로 변경하지 않는다. 기능 변경이 필요하면 실제 의존성과 승인 범위를 구분한다.

실제로 지정되지 않은 새로운 담당자나 승인권자를 만들어 작업을 넘기지 않는다.

## 3. 성공 기준

성공은 **현재 요청의 최종 결과**를 기준으로 판단한다.

| 요청 범위 | 완료 기준 |
| --- | --- |
| 조사 | 확인된 원인·근거·필요한 다음 행동 |
| 코드 수정 | 실제 결함 수정과 관련 검사 통과 |
| 운영 설치 | 실제 설치 SHA·대상 파일·사후검사 확인 |
| 실행 복구 | 기존 승인 경로에서 실제 작업 완료 |
| 게시 복구 | 실제 저장·재조회·공개 결과 확인 |
| 공통 프로세스 개선 | 관련 실제 작업이 개선된 경로로 완료된 증거 |

PR 생성·CI 통과·인계 Issue 생성만으로 운영 완료를 선언하지 않는다.

코드 수정까지 요청받았다면 운영 설치를 임의로 추가하지 않는다. 반대로 운영 복구까지 승인받았다면 코드 수정에서 멈추지 않는다.

## 4. 작업 시작 방법

현재 목표와 필요한 범위만 확인한다.

1. 사용자가 원하는 최종 결과
2. 마지막으로 유효하게 완료된 단계
3. 처음 충족되지 않은 조건 또는 실제 오류
4. 현재 승인 범위와 사용할 기존 실행 경로
5. 실제 대상 PC·계정·설치 소스

최신 지침·실제 코드·현재 변경 상태를 필요한 만큼 확인한다. 같은 대화에서 이미 확인한 문서·이력·검사를 처음부터 반복하지 않는다.

과거 checkout이나 보고서를 현재 운영 상태로 간주하지 않는다. 동시에 유효한 실제 운영 증거를 현재 도구의 접근 실패만으로 무효화하지 않는다.

## 5. 문제 분석 방식

**오류 이름보다 오류를 발생시킨 조건을 확인한다.**

다음 순서로 분석한다.

1. 실제로 무엇이 실패했는지 한 문장으로 정의한다.
2. 마지막 정상 지점과 첫 실패 지점을 연결한다.
3. 가능한 원인을 구분할 수 있는 증거를 찾는다.
4. 영향 범위가 작은 조회나 시험으로 가설을 확인한다.
5. 확인된 원인만 최소 수정한다.
6. 요청 범위의 실제 결과를 확인한다.

`BLOCKED`, `UNKNOWN`, `ACCESS_DENIED` 같은 상태명을 원인으로 반복 보고하지 않는다.

원인이 미확정이면 **확정 사실·가설·부족한 증거**를 구분한다. 기존 코드의 결함인지, 이번 변경에서 도입된 결함인지 변경 이력으로 확인한다.

## 6. 실행 환경을 먼저 맞춘다

구현 전에 해당 기능이 실제로 사용하는 환경 조건을 확인한다.

- 대상 물리 PC와 Runner
- 실행 계정과 파일 생성 계정
- 실제 경로와 접근 권한
- Task의 숨김 여부와 실행 상태
- Windows API의 가시성·계정별 조회 한계
- 실제 설치 SHA와 승인 소스
- 정상적인 Git 줄바꿈 등 플랫폼 차이

다른 계정의 사용자 TEMP에 있는 파일을 읽지 못했다면 먼저 생성·소비 계정과 저장 위치의 계약을 확인한다. Runner 전체 관리자 실행이나 사용자 프로필 전체 ACL 허용을 기본 해결책으로 삼지 않는다.

현재 사용할 수 있는 공식 경로를 재사용한다. 새 서비스 계정·공유 폴더·Runner·중계기를 먼저 만들지 않는다.

## 7. 상태와 원인을 분리한다

다음 상태를 서로 혼동하지 않는다.

- 요청 접수 완료
- Runner 배정 대기
- 실제 실행 중
- 실행 결과 미확정
- 자동화 도구 접근 불가
- 실제 기능 실패
- 실제 결과 검증 완료

예를 들어 다음 주장은 성립하지 않는다.

- Job이 queued이므로 Controller가 고장 났다.
- Task 인스턴스가 조회되지 않으므로 Core가 중단됐다.
- 결과 파일이 없으므로 운영 파일은 변경되지 않았다.
- 봇이 인계를 접수했으므로 담당 AI가 작업을 시작했다.
- HTTP 200이므로 필요한 데이터가 정상이다.

자동 AI 처리가 구성되지 않았다면 `NOT_CONFIGURED`로 명시한다. 접수·분류·댓글 작성을 실제 AI 처리 완료로 표현하지 않는다.

## 8. 검사와 차단 조건을 추가하는 기준

새 조건을 추가하기 전에 다음을 설명할 수 있어야 한다.

- 어떤 실제 오류나 운영 효과를 방지하는가?
- 해당 조건이 없으면 어떤 문제가 발생하는가?
- 기존 조건과 중복되는가?
- 이 작업에만 적용해야 하는가?
- 충족하지 못하면 사용 가능한 정상 해결 경로가 있는가?

설명할 수 없는 조건을 전역 차단으로 추가하지 않는다.

관측되지 않았다는 이유만으로 실패로 판정하지 않는다. 불확실한 쓰기는 보류할 수 있지만, 독립적인 읽기·준비·다른 기능까지 함께 막지 않는다.

불필요한 조건은 제거하거나 적용 범위를 줄인다. 다만 실제 데이터 무결성·권한·동시 변경·공급자 제한을 근거 없이 완화하지 않는다.

## 9. 작업이 막혔을 때

막힌 조건을 보고하고 끝내지 않는다.

- 필요한 manifest가 없으면 현재 승인 범위에서 정확한 변경 목록·해시·복귀 계약을 준비한다.
- 실행 경로가 없으면 기존 경로의 실제 누락 지점을 찾아 연결 가능성을 판단한다.
- 권한이 맞지 않으면 작업·계정·경로의 연결을 확인한다.
- 결과가 불명확하면 기존 원장·실제 파일·저장값부터 대조한다.
- 시간 초과가 발생하면 반영 상태와 checkpoint를 확인한 뒤 재시도 여부를 결정한다.

새 승인이 정말 필요하면 **준비된 구체적인 실행물과 추가 운영 효과**만 제시한다. 이미 승인된 범위를 반복 승인받지 않는다.

같은 원인으로 같은 요청을 무조건 재실행하지 않는다. 재시도는 새로운 증거·상태 변화·오류 유형·멱등성과 기존 실행 종료 여부를 근거로 판단한다.

## 9-1. 사용자 수동 실행 전가 방지 — 2026-11-24 #2960 교훈

**기본 책임:** 기존 승인 업무의 PC 실행·결과 회수는 자동화 담당자가 기존 Runner·독립 유지보수기 등 **실제로 검증된 정규 경로**로 완료한다. ChatGPT 도구에서 직접 Windows 명령을 실행할 수 없다는 사정만으로 사용자에게 CMD/PowerShell/Node/복구 명령 실행, 로그 복사·전달, 설치·잠금 해제를 요청하거나 "사용자가 해야 한다"고 단정하지 않는다. 지침상 사용자 직접 인증·실행이 명시된 C급 단계는 그 정확한 계약에 따른다.

**실행 경로 단절 시 순서:**
1. 원본 Issue/requestId, 유효한 성공 Run·JSON/TXT·운영 journal/lease 및 기존 승인·설치 SHA부터 계승한다. 변경 없는 성공 검증이나 원본 쓰기 요청은 반복하지 않는다.
2. 과거 **같은 효과**가 어떤 물리 PC·Windows 사용자·실행기·수신 경로·명령 계약에서 실제 성공했는지 확인한다. 예: #319의 독립 복구 성공은 독립 Windows 운영자의 존재와 실행 절차의 증거이나 #2960 설치 후 상태에 `abort-untouched`를 사용해도 된다는 증거는 아니다. `pc-job` Runner A 성공은 Controller 복구 B 권한의 증거가 아니다.
3. 현재 연결된 공식 도구에서 **정확한 효과를 허용하는 실행 수단**을 찾고, 기존 유지보수 Receiver의 지원 operation·승인 manifest·owner/CAS·부작용을 확인한다. 수단 부재·접근 불가와 운영 PC 기능 장애를 구분한다. 임의 shell, Runner 우회, 새 Workflow/예약/중계기/서비스 계정, 기존 안전 검사 완화로 해결하지 않는다.
4. 실제로 실행 가능한 정규 경로가 있으면 해당 승인 계약의 단회 실행→원본 결과·실PC 상태 재조회까지 수행한다. 없다면 `AUTOMATION_BLOCKED`를 정확한 **연결/권한 단계**에만 기록하고, 기존 자동화 경로를 복구할 수 있는 승인된 도구·소스 수정과 독립 진행을 계속한다. 성공 증거 없이 실행·설치·복구 완료를 주장하지 않는다.
5. 사용자의 직접 조작이 **계약상 필수인 C급 또는 물리적/인증 단계**일 때에만 정확한 목적·준비 상태·화면·실행 횟수·정상값·STOP 조건·회수할 결과를 제시한다. 단순히 현재 대화의 도구가 없다는 이유로 수동 작업을 "필수"라고 만들지 않는다.

**금지되는 보고 패턴:** "정상 운영 방식이 아니지만 사용자가 명령을 직접 실행해야 한다"는 식의 책임 전가, 검증되지 않은 명령을 즉시 실행하라는 안내, 같은 요청의 재제출 또는 의미 없는 진단 재실행. 실행 경로가 미연결이면 그 한계를 솔직히 보고하되, 사용자에게 실행 책임을 이전하지 않는다. 이 지침은 새로운 복구 권한이나 운영 우회 승인을 만들지 않는다.

## 10. 최소 변경과 복귀

기존 공통 실행기·원장·결과 형식·유지보수 경로를 우선 재사용한다.

변경 작업에는 효과에 맞는 다음 정보를 포함한다.

- 정확한 대상과 변경 범위
- 이전 정상 상태
- 원본 확인 또는 CAS 조건
- 백업·복귀 방법
- 복귀 확인 방법
- 결과 불명이나 동시 변경 시 중단 조건

장애 발생 시 검증된 정상 상태로 복귀할 수 있다면 운영 복구를 우선한다.

DB·D1·외부 게시에는 파일 복사와 다른 복원·보상 방식이 필요할 수 있다. 모든 변경을 같은 방식으로 되돌릴 수 있다고 가정하지 않는다. 순수 읽기 작업에 불필요한 롤백 절차를 요구하지 않는다.

## 11. 검증 방법

변경된 실패 조건과 영향 범위에 맞춰 검사한다.

- 정상 동작
- 실제로 발생한 실패 조건
- 관련 경계·오류 처리
- 기존 기능과 보호 대상의 유지

Windows API 동작을 바꿨다면 fixture만으로 운영 호환성을 확정하지 않는다. 가능한 승인 환경에서 해당 Windows 조건을 확인한다.

기존 source·설정·환경에 유효한 검사는 재사용한다. 같은 검사를 반복하거나 테스트 수를 늘리는 것을 성과로 삼지 않는다.

명확하게 구분해서 보고한다.

- fixture 검사
- Windows 네이티브 시험
- 설치 검증
- 실제 운영 검증
- 사용자 수동 검증

실제 운영에서 확인한 성공을 자동화 도구의 제약 때문에 취소하지 않는다.

## 12. 092 사례에서 유지할 기준

092는 숨김 Core Task가 실행 중이어도 `GetInstances(0)`에서 인스턴스가 보이지 않는 조건을 놓쳤다.

따라서 관련 기능을 수정할 때는 다음을 구분한다.

- 실제 실행 중인 Task
- 숨김 Task의 조회 가시성
- 정상 idle
- 조회 중 실행 종료
- 정확한 Task·Node·승인 소스의 연결
- 실행 종료 후 남은 결과의 출처 연결

한 API의 빈 결과를 실제 중단 증거로 사용하지 않는다. 공식 대체 조회를 사용하더라도 정확한 대상과 실행 계보를 확인한다.

이미 완료된 092의 실제 설치·운영 증거는 재사용한다. 동일 API를 사용하는 다른 코드도 모두 결함이라고 단정하거나 일괄 수정하지 않는다.

이 사례는 Windows 전용 추가 Gate를 만들라는 뜻이 아니라, **실제 환경의 API 동작을 확인하고 관측 한계를 정확하게 판정하라는 기준**이다.

## 13. 속도와 정보량 개선

봇 댓글과 결과 보고에는 다음 정보가 먼저 보여야 한다.

1. 현재 상태
2. 마지막 정상 지점
3. 첫 실패 조건 또는 대기 이유
4. 운영 변경 여부
5. 바로 수행할 다음 행동
6. 근거가 있는 원본 결과 링크

정상 작업에 긴 진단 보고서를 강제하지 않는다. 동일 상태의 댓글·인계·진단을 반복 생성하지 않는다.

속도 개선은 실제 접수·배정·실행·결과 회수 시간을 비교해 평가한다. 근거 없는 개선율이나 완료율을 만들지 않는다.

## 14. 완료 보고

기본 형식은 다음과 같다.

**판정:** DONE / BLOCKED / AUTOMATION_BLOCKED / STATE_UNKNOWN

**핵심 변경:** 무엇을 왜 바꿨는가  
**검증:** 실제 수행한 검사와 결과  
**운영 증거:** 실제 설치·실행·저장 결과와 링크  
**남은 문제:** 현재 목표를 막는 문제만 명시  
**다음 행동:** 남은 필수 실행 한 가지, 또는 요청 범위 완료

구현·병합·설치·운영 검증을 구분한다. 일부 완료를 전체 완료로 표현하지 않는다.

## 15. 이 지침의 적용

이 파일을 해당 담당 브랜치에 저장하고 `AGENTS.md`에서 참조한다.

다음 작업부터 실제 작업 방식에 적용한다. 파일 저장이나 “학습 완료” 응답만으로 적용 완료라고 주장하지 않는다.

현재 승인 범위의 작업을 **실행 → 필요한 확인 → 실제 결과 검증 → 완료**로 이어가는 것이 기준이다. 새로운 절차를 추가하는 것보다 기존 절차에서 불필요한 반복과 단절을 제거하는 것을 우선한다.
