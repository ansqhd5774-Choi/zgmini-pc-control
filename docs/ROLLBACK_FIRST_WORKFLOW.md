# 정상 운영 복귀 우선 — 공통 변경 작업 기준

2026-11-21 사용자 결정. Controller 한 건에 한정하지 않고 코드·설정·설치·배포·DB·게시 등 승인된 변경 작업에 적용한다. 이 문서는 새 승인서나 전역 Gate를 만들지 않는다.

## 기본 흐름

**검증된 정상 상태 보존 → 후보 준비·해당 범위 시험 → 적용 → 실제 결과 확인 → 확정 실패면 정상 상태 복귀 → 복귀 확인 → 실패 후보의 원인 분석.**

운영이 멈춘 상태에서 원인 분석·문서 작성·진단기 추가부터 반복하지 않는다. 정상본을 되살릴 수 있으면 서비스 복구를 먼저 수행한다. 후보의 실패와 기존 운영의 정상 복귀는 별도 판정한다. `ROLLED_BACK`은 후보 설치 성공이 아니다.

## 작업에 포함할 복구 정보

기존 manifest·계획·journal·백업에 아래 내용을 함께 담는다. 같은 정보를 별도 승인 파일로 다시 만들지 않는다.

- 이번에 바꾸는 정확한 파일·설정·데이터 키와 현재 버전/해시.
- 복원할 이전 상태와 검증된 백업 위치. 이미 유효한 백업·정상 Runtime 증거는 재사용한다.
- 정상/실패/결과 불명의 실제 판정 기준과 기존 복원 실행 경로.
- 복귀 시 영향을 받는 프로세스·예약·접수의 원래 상태 및 확인 방법.
- 원래 변경 실패와 복구 실패의 코드·원장·결과를 각각 보존할 위치.

읽기 전용 작업에는 데이터 백업·롤백을 억지로 요구하지 않는다. 후보 생성·검사 실패로 운영이 바뀌지 않았다면 정상본을 그대로 유지하고 실패 후보만 보존한다.

## 변경 종류별 복귀

| 종류 | 정상 복귀 단위와 확인 |
|---|---|
| 코드·파일·설정 | 이번 변경 파일과 대응 설정만 원본 바이트로 복원하고 실제 버전·기동·보호 해시 확인 |
| Controller·Writer·유지보수기 | 기존 독립 실행기와 검증 백업 사용. 신규 시작 억제 → 기존 실행 정상 drain → 범위 내 복원 → 원래 실행/접수 재개 → 실제 readback |
| 웹 배포 | 검증된 이전 배포본과 그 설정 조합으로 복귀하고 실제 페이지·API 확인. Git 되돌림만으로 배포 복귀를 주장하지 않음 |
| DB·schema | 변경 전 대응 상태·트랜잭션·역방향 migration 또는 보상 변경을 준비. 다른 작업의 새 행이나 정상 수정은 전체 DB 복원으로 지우지 않음 |
| D1·공개 게시 | 정확 키의 이전 값과 현재 버전을 고정한 CAS 복원/정정. 다른 게시자가 전진시킨 값은 덮어쓰지 않음. 저장값·공개 응답 재조회 |
| 공급자 호출·외부 발송 | 이미 소비된 호출·발송은 되돌릴 수 있다고 주장하지 않음. 추가 실행 중지 및 지원되는 취소/정정으로 효과를 제한 |

해당 adapter에 없는 DB/게시 복귀 기능을 문서만으로 구현됐다고 보고하지 않는다. 담당자는 자기 작업에 필요한 범위의 기존 복구 기능을 재사용하거나 보완한다. 다른 기능의 복구 지원 여부를 정상 업무 전체의 선행조건으로 붙이지 않는다.

## 실패와 결과 불명의 처리

- 실제 실행 실패가 확인되고 백업·소유권·변경 범위가 일치하면 같은 승인 작업 안에서 검증된 정상본 복귀를 우선한다. 동일 범위의 복귀를 다시 승인받기 위해 운영을 장기간 멈추지 않는다.
- 업로드가 없더라도 원래 Issue·Run·Job·Runner와 실행 단계의 terminal failure가 입증되면 실패로 분류할 수 있다. 단순 timeout·취소·403·응답 없음은 실패 확정 증거가 아니다.
- 결과 불명은 원장·실제 값·프로세스·checkpoint부터 읽는다. 실행 중인 작업을 실패로 간주해 종료하거나 같은 요청을 다시 실행하지 않는다.
- 정상본 복귀를 확인한 범위는 기존 승인 업무를 계속한다. 실패한 후보 수정은 별도로 진행하며 전체 작업을 재승인·재진단 대기로 묶지 않는다.
- 복구 중 CAS 불일치·다른 작업의 변경·백업 변조·중간 중단이 확인되면 그 복구 범위만 멈추고 원본·백업·lease·진행 원장을 보존한다. 강제 덮어쓰기·lock 삭제로 성공을 만들지 않는다.

## 공통 실행 경로에 반영한 동작

Controller의 `tools/update.mjs`는 결과 업로드가 누락된 경우에도 정확한 원본 Actions 실행 단계의 확정 실패를 조회한다. `tools/maintenance-contract.mjs`의 공통 증거 검증이 통과한 실패만 기존 자동 롤백으로 연결한다. `tools/maintenance-apply.mjs`는 이전 버전 재기동·접수·backlog·최종 Runtime을 확인하고 원래 실패와 복귀 실패를 별도 기록한다.

Writer B는 설치 후 Core가 재개된 시점에 실패해도 `prepareRollback`으로 같은 승인 유지보수 창을 다시 확보하고 정상 drain 후 원본 source/config를 복원한다. 활성 Core 강제 종료는 하지 않는다. 원본 Task·파일·설정·보호 상태가 확인된 후에만 설치 소유권을 정리한다.
