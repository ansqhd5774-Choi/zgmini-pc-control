# 공용 Controller 적용 대기열 운영 방침

이 문서는 일반챗 간 공용 설치 조정 규칙이다. 실제 PC 잠금·승인·설치기를 대체하거나 새 자동 실행기를 구현하지 않는다. 기존 설치 결과는 [실측 기록](PC_AUTOMATION_RUNTIME_20261103.json)을 재사용하고, 현재 설치 SHA는 필요한 적용 직전에 조회한다.

## 단일 조정 원장과 담당

현재 단일 조정 원장은 [공용 Controller 적용 대기열 #68](https://github.com/ansqhd5774-Choi/zgmini-pc-control/issues/68)이다. 관련 작업자는 이곳에 등록하며 대화별로 새 대기열을 만들지 않는다. 원장을 교체할 때는 기존 원장에 대체 위치와 인계를 기록한다. 기존 요청·승인·결과 Issue는 삭제하지 않는다.

이 문서 자체에는 변하는 설치 SHA나 미확인 PR 상태를 고정하지 않는다. 조정 원장에는 적용 담당 한 명과 적용 중인 항목을 명시한다. 담당이 미지정이면 준비된 작업의 담당자가 현황·실행 순서와 담당안을 등록해 확정한다. 대기열의 담당 기록과 PC의 실제 유지보수 원장·lease를 적용 직전에 함께 확인하며, 경합 중에는 둘이 동시에 적용하지 않는다.

기능 담당은 개발·테스트·승인 증거를 준비하고, 적용 담당은 공용 배포 묶음·설치 순서·결과를 관리한다. 기존 적용 담당을 임의로 덮어쓰지 않고 명시적 인계로 변경한다. Issue 기록은 원자적 잠금이 아니므로 실제 적용에는 기존 PC lease를 사용한다. 조정 역할은 새 승인 권한이나 다른 작업자의 코드 변경 권한을 뜻하지 않는다.

## 등록할 최소 정보

| 필드 | 기록 내용 |
|---|---|
| 항목 ID·기능 담당 | 기존 요청/Issue 링크와 담당 대화 식별자 |
| 대상 | Controller 또는 유지보수기, PR·정확한 source SHA |
| 설치 기준 | 실제 설치 SHA와 관측 시각 |
| 변경·승인 | 파일 목록·해시, 각 변경의 승인 근거, 실제 검사 증거 |
| 의존성 | 선행 항목 ID, 필요한 정책·Windows 검증·인계 |
| 적용 계획 | 묶음 ID 또는 순서, 적용 담당, 다음 실행 조건 |
| 결과 | 실제 적용 SHA, 모듈별 실행·결과 회수, 보호 상태, 남은 문제 |

조정 상태는 `등록`, `적용 준비`, `승인 필요`, `선행 작업 대기`, `적용 중`, `검증 완료`, `복구 확인 필요`로 구분한다. 이 명칭은 작업 조정용이며 실행기의 JSON schema나 Runtime status를 변경하지 않는다.

## 실행 순서

1. 적용 중인 요청·원장·lease와 실제 설치 SHA를 확인한다. 실행 중이면 정상 종료를 기다리고 소유권을 중복 주장하지 않는다.
2. 설치 SHA부터 후보 목표 SHA까지의 실제 누적 diff를 각 PR·승인에 연결한다. main에 병합됐다는 사실만으로 승인됐다고 판정하지 않는다.
3. 승인·검사가 완료되고 호환되는 변경은 통합 manifest로 묶는다. 공통 파일의 최종 바이트와 해시는 실제 목표 커밋 기준으로 고정한다. 각 변경의 개별 승인 범위는 그대로 유지한다.
4. 미승인 변경이 섞이면 검증된 선별 경로로 분리하거나 필요한 승인만 확인한다. 분리가 어렵다면 승인된 선행 목표부터 순차 적용한다. 불필요하게 모든 작업을 중단하지 않는다.
5. 정책 변경이 필요한 항목은 해당 유지보수 정책의 승인·Windows 검증·인계를 선행시킨다. 다른 정책으로 이미 가능한 항목은 독립적으로 진행한다.
6. 실제 승인 범위·정확한 manifest·기존 독립 유지보수 경로로 적용한다. 적용 담당도 기존 도구·권한·idle·보호 검사를 우회할 수 없다.
7. 설치 후 실제 SHA, 보호 검사, 재연결 및 필요한 모듈별 Runtime 결과를 기록한다. 공통 사후 검사 PASS만으로 새 모듈 자체의 실행 성공을 대신하지 않는다.
8. 다음 항목은 새 실제 설치 SHA로 명세를 갱신한다. 성공·확인된 실패 모두 기록하고 담당 교체 시 미완료 요청·현재 단계·복구 상태를 인계한다.

`ALLOWFILE_DIFF_MISMATCH`는 승인 범위와 누적 변경을 다시 맞춰야 하는 상태다. 검사를 없애거나 누락 파일을 근거 없이 전부 허용하지 않는다. timeout·통신 오류·부분 반영에서는 실제 상태를 먼저 대조하고 재요청하지 않는다.

## 무기한 상호 대기 방지

- “다른 담당자 대기”만 보고하지 않고 선행 항목 ID·적용 담당·해제 조건을 제시한다.
- A가 B를, B가 A를 기다리면 원장에서 순환 의존성을 해소해 하나의 묶음이나 명확한 선후 관계로 바꾼다.
- 담당이 없다는 사실을 방치하지 않고 준비된 항목의 담당자가 조정안을 등록한다.
- 준비가 덜 된 항목은 그 이유와 다음 조건을 기록하며 무관한 준비 완료 항목까지 막지 않는다.
- 모든 기능의 개발·검토·격리 시험을 직렬화하지 않는다. 공유 설치·운영 쓰기만 직렬화한다.
- 기존 설치기가 처리할 수 있는 일을 별도 CMD·Runner·예약 작업 추가로 해결하지 않는다.

## 보고 예시

`선행 작업 대기: 항목 <ID> / 적용 담당 <대화> / 해제 조건 <정책 인계 PASS> / 다음 실행 <실제 설치 SHA 재조회 후 manifest 작성>. 독립 코드 검토는 계속 진행.`

변하는 실제 대기열은 위 단일 Issue에 기록한다. 이 방침을 저장했다는 이유로 현재 대기 작업들이 등록·승인·설치됐다고 보고하지 않는다.
